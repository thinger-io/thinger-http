# Changelog

All notable changes to thinger-http are documented in this file. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow
[Semantic Versioning](https://semver.org/spec/v2.0.0.html), as described in
[Versioning](README.md#versioning).

## [Unreleased]

## [0.11.0] - 2026-11-09

Minor release: what servers built on 0.10 asked for to read large bodies and to serve files. A handler can bound the reads of a body with a deadline it moves as it reads, a `multipart_reader` returns the content of a part in blocks of a size of its choice, and the sizes of bodies and parts are 64-bit everywhere. A file of an unknown type goes as `application/octet-stream`, a `Content-Type` set before `send_file()` is kept, and `response::set_header()` replaces a header. An in-memory `dispatch()` returns once the `on_response()` hook has run, and building a route no longer compiles a regex of its whole pattern, which makes registering routes 2 to 15 times faster. Two breaking changes, narrow ones in source, and four behaviour changes, marked under Changed, each with its recipe in [Migrating from 0.10 to 0.11](MIGRATING.md#from-010-to-011). 0.11 is not ABI compatible with 0.10, as the SONAME `libthinger_http.so.0.11` says: rebuild what links the library (see the ABI note under Changed).

### Added

- `request::set_read_deadline(time_point)`: an absolute deadline for the reads of the body, pending and later ones (`read()`, `read_some()`, `read_body()` and those of a `multipart_reader`), as `http.ResponseController.SetReadDeadline` in Go. The handler sets and moves it as it reads, which cuts a client that goes silent or trickles without cutting a long upload. It replaces the request timeout of the connection or the route for the rest of the body, `time_point::max()` removes it, and it bounds no write. Nothing is answered for the handler (`408` if it answers nothing), and the connection closes after the response, as with any body left unread. A request that does not call it pays nothing for it. See [Request Body](README.md#request-body).
- `body_error::timeout`: what `get_body_error()` gives once a read passes the deadline, for good. A `multipart_reader` that passes it fails with `invalid_body` (`400`); `req.get_body_error()` tells it apart, to answer `408`.
- `multipart_reader::read(max_size)`: returns at most `max_size` bytes of the current part, without copying, and keeps the rest for the next call, as `Read(p)` in Go's `multipart.Part`. `read()` keeps returning each piece as it comes. `read(0)` returns empty at once without advancing, which is not the end of the part.
- `response::set_header(key, value)`: sets a header to a single value, replacing every field of that name set before, compared without case, as `res.setHeader()` in Node and `Header().Set()` in Go. `header()` still adds a field, as `res.appendHeader()` and `Header().Add()`. It has the validation and the thread rules of `header()`: an invalid header is dropped and logged at debug level, leaving the ones set before as they were. Behind it, `headers::replace_headers(key, value)`.
- `benchmark_route_registration`: the time to register 500 routes in an `http_application`.

### Changed

- **Breaking:** the byte limits of `multipart_limits` (`max_header_size`, `max_filename_size`, `max_field_size`, `max_fields_size`, `max_file_size`), `multipart_parser::part_size()`, `multipart_file::size()` and the maximum body size (`default_max_body_size`, `set_max_body_size()` and `get_max_body_size()` of `request` and `http_application`, `max_body_size()` of `route`, `route_group` and `virtual_host`, and the size given to `request::discard_body()`) are `std::uint64_t`, as Go's `int64` sizes, and hold a limit over 4 GiB in a 32-bit build. Code assigning a `size_t` compiles as before. Where `size_t` is not `std::uint64_t` (macOS, 32-bit builds), code that names the old type, such as a pointer to one of these functions or a `const std::optional<size_t>&` taken from `route::get_max_body_size()`, may need `std::uint64_t` or `auto`. The count limits (`max_parts`, `max_files`) stay `size_t`. See [64-bit sizes](MIGRATING.md#64-bit-sizes).
- **Breaking:** with `-Werror`, a `switch` over `body_error` without a `default` no longer compiles, as `body_error::timeout` is a new value. See [A new `body_error` value](MIGRATING.md#a-new-body_error-value).
- **Behavior change:** `send_file()`, `serve_static()` and `file_server::serve()` send `application/octet-stream` for a file whose extension is unknown or missing, where 0.10 sent `text/plain`, as Node's `send`. `mime_types::extension_to_type()` returns it, and `mime_types::text_plain` stays. Nothing is guessed from the content of the file, and the known extensions keep their type. These files are no longer compressed on the fly, as `application/octet-stream` is not a compressible type, and over 1 MiB they are now streamed. See [Files of an unknown type](MIGRATING.md#files-of-an-unknown-type).
- **Behavior change:** a `Content-Type` set by the handler or a middleware before `send_file()` or `serve_static()` is kept, as Node's `send` keeps it, where 0.10 replaced it with the one of the file. Whether the file is compressed on the fly follows the type actually sent. See [Headers set before the response](MIGRATING.md#headers-set-before-the-response).
- **Behavior change:** `send_response()` also sends the headers set before with `header()` or `set_header()`, which 0.10 dropped, as `header()` promised. The message's own headers win over those of the same name, as the headers given to `writeHead()` in Node; `Content-Length` and `Transfer-Encoding` set before are ignored. See [Headers set before the response](MIGRATING.md#headers-set-before-the-response).
- **Behavior change:** `form::mime_type()` and `form::file(name, path)` use the same lookup: a file without extension goes as `application/octet-stream`, where 0.10 sent `text/plain`, and a `.txt`, `.log`, `.conf` or `.text` file goes as `text/plain`, where 0.10 sent `application/octet-stream`. See [Files of an unknown type](MIGRATING.md#files-of-an-unknown-type).
- Building a `route` no longer compiles a `std::regex` of its whole pattern: `route::matches()`, which routing does not use, compiles it on its first call, safely from several threads. The constructor compiles only the regexes of the parameters, in a single `std::regex` and only for routes that have one, and accepts and rejects the same patterns (an invalid one still throws `std::regex_error`). `route` stays copyable, and copies share the compiled regex. Registering 500 routes in an `http_application` (`benchmark_route_registration`), median: without parameter regexes, 14.6 ms → 0.94 ms in Release and 596 ms → 57 ms in Debug with ASan and UBSan; with a mix of literals, parameters, regexes and wildcards, 15.5 ms → 6.9 ms and 643 ms → 303 ms. Routing costs the same.
- 0.11 is not ABI compatible with 0.10, and its SONAME is `libthinger_http.so.0.11`. `http_stream` gains a virtual function, `set_read_deadline()`, which changes its virtual table, as `asio::socket` does with `read_some_cancellable()`; `multipart_reader` and `server_connection` gain members; `multipart_reader::read()` takes an argument; and the sizes above change in layouts and signatures. Rebuild what links the library.

### Fixed

- `http_application::dispatch()` in memory now completes after the `on_response()` hook has run, in both its coroutine and callback forms, within what is left of `dispatch_options::timeout`. Before, the caller resumed as soon as the response was collected, and the hook could run after the caller had destroyed what it captures. A handler still running when the timeout ends gets its response returned without waiting; the hook then runs when the handler ends, so what it captures must live as long as the handler. Cancelling the dispatch and destroying the application still do not wait for the hook. Without a hook nothing changes.
- A chunked response sends `X-Content-Type-Options: nosniff` once when the handler set that header too.

## [0.10.0] - 2026-11-06

Minor release: what servers and clients had to work around in 0.9. CORS takes options as in Express and rs/cors, `serve_static()` can leave a path without a file to the not-found handler and `file_server::serve()` is public, each server and client choose the query parameters hidden from their logs, a server WebSocket closes with a code and a reason of its own and counts what its queue drops, and destroying an application ends its in-memory dispatches. `async_client` becomes a handle on a state its requests share, the library builds with clang 20 through spdlog 1.15.1 and fmt 11.1, and its tests pass on macOS. Seven breaking changes and fifteen behaviour changes, marked under Changed and Removed, each with its recipe in [Migrating from 0.9 to 0.10](MIGRATING.md#from-09-to-010). 0.10 is not ABI compatible with 0.9, as the SONAME `libthinger_http.so.0.10` says: rebuild what links the library (see the ABI note under Changed).

### Added

- `http::cors_options`, the options of `enable_cors()`, with the defaults of `cors()` in Express: `origins` (`{"*"}`, or a list of exact origins compared case-insensitively in ASCII, the one that matches reflected), `origin_filter` (a function that decides instead of the list), `methods` (`GET, HEAD, PUT, PATCH, POST, DELETE`), `allowed_headers` (without a value, those a preflight asks for are reflected), `exposed_headers`, `max_age` (not sent without a value, sent when 0), `credentials` (off) and `preflight_continue` (off). See [CORS](README.md#cors).
- `http_application::disable_cors()`: back to no CORS headers, and `OPTIONS` routed as any other method.
- With a list of origins or a filter, every response says `Vary: Origin`, allowed or not and with or without `Origin`, as Express and rs/cors do, merged with the other fields of `Vary`. An origin not allowed gets no `Access-Control-Allow-*` or `Access-Control-Expose-Headers`; its request still runs, as CORS is not access control.
- `static_options::fallthrough` (off by default, last member): `serve_static()` leaves a `GET` or `HEAD` for a path without a file (it does not exist, a directory without its fallback, neither a file nor a directory, a dotfile with the policy `ignore`) to the not-found handler of its host or, without one, to the answer of the host to a `GET` without a route, with the response untouched and without running the middlewares again. The fallback is then only the index of a directory. A path outside the directory, a dotfile with `deny` and a malformed path are still answered with `403` and `400`, unlike Express's `serve-static`. Without the option nothing changes. See [Fallthrough](README.md#fallthrough).
- `http::file_server::serve()` is public: its header, `http/server/file_server/static_files.hpp`, is in `public-headers.txt` and defines `http::static_options` and `http::dotfiles_policy`, which `virtual_host.hpp` still brings in. It serves a file from any handler with the guarantees of `serve_static()`, and says whether it answered. See [Serving Files from a Handler](README.md#serving-files-from-a-handler).
- `http::util::url::redacted_parameters`, a set of query parameter names, compared whole, without case and percent-decoded, with `defaults()`, `add()`, `remove()` and `contains()`. Copies share the names. `{}` redacts no parameter, and the password of the user info of a URL is redacted whatever the set.
- Each server and each client choose the names they redact: `connection_options::logging.redact`, last member of `body_logging`, and `http_client_base::redact_parameters()`, for `async_client` and the other clients too. `options.logging = {true, 512}` still compiles, and sets the names back to the defaults; `log_bodies()` leaves them. See [Query Parameters in the Logs](README.md#query-parameters-in-the-logs).
- `http::util::url::loggable_uri(uri, names)`, which redacts with the set given.
- `websocket_connection::stop(code, reason)`: closes a server WebSocket with a code and a reason of the application, from any thread, as `ws.close(code, reason)` in Node. It takes the path of any other close: the closing handshake, the queue closed and the producers waiting told `false`, the keepalive stopped, the connection out of the count of the server, and `on_close()` called once. A code that a close frame may not carry (RFC 6455, 7.4: valid are 1000–1014 without 1004, 1005 and 1006, and 3000–4999), a reason above 123 bytes or one that is not valid UTF-8 throw `std::invalid_argument` in the calling thread, without closing. Once closing or closed it does nothing else: the first code decides. `stop()` is still `1000` without a reason. See [WebSocket Close](README.md#websocket-close).
- `dropped_messages()` of `websocket_connection` and `sse_connection`: how many messages sent without waiting the overflow policy dropped since the connection was created, the new one (`drop_newest`, or `drop_oldest` with no room to make) or the older ones (`drop_oldest`), in the unit of `queued_messages()`. A 64-bit number that never decreases, readable from any thread. It does not count awaited sends, what is sent once closing or closed, what was queued when the connection closed, or an overflow with `overflow_policy::close`. See [WebSocket Flow Control](README.md#websocket-flow-control).
- `asio::websocket::close_graceful(code, reason)`: the close frame carries a reason, also when another close sends it while it waits for its turn to write. `asio::websocket::valid_close_code()` and `MAX_CLOSE_REASON_SIZE` are public.

### Changed

- **Breaking:** `enable_cors(bool enabled = true)` → `boost::system::error_code enable_cors(cors_options options = {})`, on `http_application` and so on both servers. `enable_cors()` still compiles, with the new behaviour below; `enable_cors(true)` and `enable_cors(false)` no longer compile, on purpose: use `enable_cors()` and `disable_cors()`. The result is empty when applied, and `invalid_argument`, with the reason in the log and the CORS in force unchanged, for `credentials` with any origin, `*` listed with other origins, an origin with control characters, a method or header name that is not a token, and a negative `max_age`. As in 0.9, its headers go on every response of the application, whoever answers it, on a connection or dispatched in memory; responses that never reach the application (a `dispatch()` of a null or chunked request, one whose `handle()` throws) do not have them. See [CORS](MIGRATING.md#cors) in the migration guide.
- **Behavior change:** `enable_cors()` no longer sends `Access-Control-Allow-Credentials: true` next to `Access-Control-Allow-Origin: *`, a pair that browsers reject (Fetch, CORS check), so 0.9 announced credentials to anyone and no browser could use them. To send credentials, list the origins or give a filter: `*` with `credentials` is `invalid_argument`, stricter than Express and rs/cors, which send the pair. The library never sends the pair, even when a filter allows an `Origin: *` or a handler or `start_stream(head)` sets `*`. See [CORS](MIGRATING.md#cors).
- **Behavior change:** the responses to a request that is not a preflight no longer have `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers`, which only a preflight reads: they have `Access-Control-Allow-Origin`, and `Access-Control-Allow-Credentials` and `Access-Control-Expose-Headers` when configured. See [CORS](MIGRATING.md#cors).
- **Behavior change:** `enable_cors()` answers preflights (an `OPTIONS` with a non-empty `Access-Control-Request-Method`, as Fetch and rs/cors define it) with `204` and no body, on any path and host, before route matching and without running any middleware or handler, as `cors()` mounted first in Express and rs/cors do: a browser sends them without credentials, so an authorization middleware would reject them. In 0.9 they reached the routes and ended in `404` or `405`. `on_response` is called for them, an unread body follows the rules of any unread body so that the connection stays in sync, and [`dispatch()`](README.md#in-memory-dispatch) answers the same. Any other `OPTIONS` is routed as usual. `preflight_continue` lets them follow the normal path instead (route matching, middlewares with the matched route visible, the `OPTIONS` route of the application or `404`/`405`/the not-found handler), with the preflight headers already on the response, as `preflightContinue` in Express and `OptionsPassthrough` in rs/cors. See [CORS](MIGRATING.md#cors).
- **Breaking:** the public constructors of `response` no longer take `bool cors_enabled`: the application sets what CORS needs on the response before handing it to the handler. A `response` built by hand has no CORS headers. See [CORS](MIGRATING.md#cors).
- **Behavior change:** a CORS header set by a handler or a middleware, with `header()` or in a message given to `send_response()`, replaces the one of `enable_cors()`, as `res.setHeader()` after `cors()` does in Express. In 0.9 the response could have both, as they were added one after the other. See [CORS](MIGRATING.md#cors).
- **Behavior change:** the `Vary` of a head given to `start_stream()`, such as the one a target sends through `reverse_proxy`, is merged with the `Vary` already on the response (from `enable_cors()` or `header()`) instead of replacing it; `*` stays alone. Any other header of the head still replaces the one with the same name, and a response with no `Vary` of its own sends that of the head as it came. See [CORS](MIGRATING.md#cors).
- `res.encode()` merges `Accept` into the `Vary` of the response instead of adding a second `Vary` field.
- **Breaking:** `void file_server::serve(req, res, directory, options)`, which read the parameter `path` of the route, → `bool file_server::serve(req, res, directory, path, options)`, where the caller gives the raw path, and the result says whether it answered. See [Static files](MIGRATING.md#static-files).
- **Breaking:** `route_handler::handle_unmatched(std::shared_ptr<request>, response&)` → `route_handler::handle_unmatched(request&, response&)`. See [Static files](MIGRATING.md#static-files).
- **Behavior change:** more query parameters are hidden from the logs by default. To the eight of 0.9 (`access_token`, `authorization`, `token`, `api_key`, `apikey`, `key`, `password`, `client_secret`) join `code`, `id_token`, `refresh_token`, `secret`, `sig`, `signature`, `x-amz-security-token`, `x-amz-signature` and `x-goog-signature`: the one-time codes of a password reset, an email verification or OAuth, the other OAuth and OIDC tokens, and the signatures of presigned URLs (S3, GCS, Azure SAS). `GET /cb?code=abc&state=s` is logged as `GET /cb?code=[redacted]&state=s`, and `http::util::url::loggable_uri()` returns that. See [Query parameters in the logs](MIGRATING.md#query-parameters-in-the-logs).
- **Behavior change:** `websocket_connection::stop()`, with or without arguments, and the close of a server shutdown end within `asio::websocket::CLOSE_TIMEOUT` (5 seconds) of the call, whatever the peer does, as `Conn.Close()` of Go's `coder/websocket`. In 0.9, with a peer that did not read and a message being written, the close frame waited for the `write_timeout` (60 s by default, up to 75 s with its watch of the socket, and with no limit if `0`) and the connection ended in `1013`. Now the socket is closed at the deadline without the handshake, and `on_close()` gets the code asked for if its frame was written whole and `1006` if not, never `1013`. A message still being written at the deadline is cut, even to a slow client that keeps reading: to get it out first, await its send before `stop()`. See [WebSocket close codes and dropped messages](MIGRATING.md#websocket-close-codes-and-dropped-messages).
- **Behavior change:** when this end sent its close frame and the peer ended the connection without answering, `on_close()` of `websocket_connection` gets the code sent, as documented for a peer that does not answer, instead of `1006`. See [WebSocket close codes and dropped messages](MIGRATING.md#websocket-close-codes-and-dropped-messages).
- **Behavior change:** `asio::websocket::close_graceful()`, also through `websocket_client::close_async()`, has one deadline of `CLOSE_TIMEOUT` from its first call, its wait for the turn to write included, where only the wait for the answer of the peer was bounded. A later call does not start it over. A close frame not written whole by the deadline is reported as `1006`. See [Behaviour changes to check](MIGRATING.md#behaviour-changes-to-check-in-010).
- **Behavior change:** destroying an `http_application` or a server ends its in-memory dispatches in flight without waiting for them, from any thread or from one of their handlers. One without a complete response ends at once, with `operation_aborted` when awaited and `503 Service Unavailable` with a callback; a complete one is delivered; one not started runs no middleware or handler; a running handler is interrupted as at the shutdown of a server, whatever its route declared, and what it sends afterwards is dropped. See [In-Memory Dispatch](README.md#in-memory-dispatch) and [`dispatch()` when the application is destroyed](MIGRATING.md#dispatch-when-the-application-is-destroyed).
- **Behavior change:** a handler whose scope another reason cancelled first, and whose route let it go on, is now interrupted when the server reaches its shutdown deadline, is stopped or is destroyed, while its connection still follows the request (for instance, a `504` of its route timeout not written yet): its next cancellable await, and a wait bound to `req.cancellation_slot()`, end with `operation_aborted`, and `req.cancelled()` keeps the first reason. In 0.9 it ran on. A handler still running once its response is written is not reached, as before: the connection no longer follows the request. See [Cancellation](README.md#cancellation) and [`dispatch()` when the application is destroyed](MIGRATING.md#dispatch-when-the-application-is-destroyed).
- **Behavior change:** the `async_client` no longer guards its coroutines with an executor of its own: every request holds what it uses of the client by `shared_ptr` (its settings, connections and TLS contexts), and `stop()` and the destructor cancel, close and, where they can, wait. For callbacks nothing changes: the callback of a request cancelled is not called once they returned, from any thread, one running is not interrupted, a call from a thread that is not one of the workers waits for it as long as it takes, and the destructor on a worker still waits for those running on other workers. Neither does anything change for coroutines stopped from a thread that is not one of the workers, as they end before the call returns. The one guarantee that 0.9 gave and 0.10 does not (the entry B7 of 0.9.0, "none of them resumes anymore"): after `stop()` or the destructor called from a worker, a coroutine of `run()`, or a callback that is a coroutine, may resume after the call returned, and its frame is destroyed on its worker. It sees `operation_aborted`, or the correct response of a request that completed before the cancellation reached its worker. What it uses must stay alive, the `async_client` included, which the requests do not hold: capture it by `std::shared_ptr`, call `client->stop()` in the callback and release the reference; or stop the client from a thread that is not one of the workers. See [Async Client](README.md#async-client-async_client) and [`async_client`: coroutines that may resume after the client](MIGRATING.md#async_client-coroutines-that-may-resume-after-the-client).
- **Behavior change:** a coroutine that ignores the cancellation is still waited for up to 1 s by `stop()` and the destructor called from a thread that is not one of the workers, and left behind then. In 0.9 it was dropped at its next resumption; now it holds what it uses of the client and ends by itself, and may resume after the call returned, as above. A callback that is a coroutine counts as such, and not as a callback running, which is waited for as long as it takes. See [`async_client`: coroutines that may resume after the client](MIGRATING.md#async_client-coroutines-that-may-resume-after-the-client).
- **Behavior change:** the coroutines of `async_client::run()` run on the executor of the io_context of their worker, with no wrapper, as they did before 0.9: `asio::io_context_of(co_await this_coro::executor)` returns their worker's io_context where it returned null, `executor_client::for_current_coroutine()` still works in them, and work the application spawns on that executor is no longer dropped when the client stops: it is the application's, as the WebSockets are. To have it cancelled with the client, start it with `client.run()`. See [`async_client`: coroutines that may resume after the client](MIGRATING.md#async_client-coroutines-that-may-resume-after-the-client).
- **Breaking:** `async_client` no longer derives from `http_client_base`. It is a handle on a state its requests share, and has the same public methods with the same signatures (the setters still return `http_client_base&`), so code calling them compiles as it is. An `async_client` no longer converts to `http_client_base&`, no longer takes `client.http_client_base::get(...)`, and a class deriving from it no longer reaches the protected members of `http_client_base`. `<thinger/http/client/async_client.hpp>` no longer includes `<condition_variable>`. See [`async_client` is no longer an `http_client_base`](MIGRATING.md#async_client-is-no-longer-an-http_client_base).
- An `async_client` request costs less, as what the removed machinery did on every resumption is gone. User-space instructions per request of an `async_client` with one worker making N sequential keep-alive `GET` against a local server in another process, each request launched from the callback of the previous one (Release, GCC 13, x86-64, median of 5 runs): 60,475 in 0.9.2 and 55,109 now with N = 10,000 (-8.9 %), 60,285 and 54,919 with N = 20,000 (-8.9 %). Coroutines of `run()` awaiting the requests in a loop go from 55,526 to 51,085 (-8.0 %). In the code, 436 lines of `thinger/` went and 408 came, about 50 of them forwarding one-liners as `async_client` no longer inherits its methods: `async_client.hpp` and `async_client.cpp` have 736 lines, 741 in 0.9.2.
- **Breaking:** the spdlog thinger-http downloads goes from `v1.12.0` (fmt 9.1) to `v1.15.1` (fmt 11.1), and its consumers see that fmt through `spdlog::spdlog`. fmt 9.1 does not compile with clang 20 or later, and `v1.15.1` is the oldest spdlog that does (`v1.15.0`, fmt 11.0, still fails). A project no longer has to define `FMT_CONSTEVAL` to build, which turned off the compile-time check of format strings: remove it, and an invalid format such as `LOG_INFO("{} {}", 1)` stops the build again. The functions and macros of `thinger/util/logger.hpp` and the text of the library's log do not change, but code of yours that formats its own types may not compile with fmt 11: see [spdlog and fmt](MIGRATING.md#spdlog-and-fmt).
- **Behavior change:** an installed spdlog is used only from 1.15.1 on: an older one, such as the 1.12.0 of Ubuntu 24.04, is ignored and `v1.15.1` is downloaded, as when none is installed. A `spdlog::spdlog` target or a `FetchContent_Declare(spdlog)` your project made first stays, whatever its version. An installed spdlog is now found globally, so a parent project sees its `spdlog::spdlog` as it sees the downloaded one. See [spdlog and fmt](MIGRATING.md#spdlog-and-fmt).
- 0.10 is not ABI compatible with 0.9, and its SONAME is `libthinger_http.so.0.10`. With the change of hierarchy, the layout of `async_client` changes and it has no vtable any more; `http_client_base` loses a virtual function (see Removed), which changes the vtable of `client` and `executor_client`; and other classes gain members, such as `static_options` and `body_logging`. Rebuild what links the library.

### Removed

- **Breaking:** `route_handler::enable_cors()`, with no replacement in the router: the hidden `OPTIONS :path(.*)` route it registered had no metadata, so a middleware requiring route metadata rejected the preflights it was meant to answer. `enable_cors()` of the application answers them without a route, and nothing of CORS is in the route table or the OpenAPI document. See [CORS](MIGRATING.md#cors).
- The internals behind the guarantee of `async_client` that coroutines do not resume (see Changed): `detail::request_scope` with its epochs, `detail::request_io_context()`, the gated executor every resumption of a request went through, and its per-thread count of what was running. Of what remains, `stop()` and the destructor keep a bounded grace of 1 s, which no longer drops anything.
- `http_client_base::websocket_executor()`, a protected virtual only `async_client` overrode. It breaks no source and changes the vtable of `http_client_base`, so of `client` and `executor_client`.

### Fixed

- A WebSocket over a Unix socket did not take the logging options of its client: its request line used the defaults.

A dispatch now shares only the serving state (see Changed).

Patch release: the memory a WebSocket frame header could make the server take, header names and values set by the application, the synchronous WebSocket client on worker threads, dotfiles, long paths, `stop()` and TLS renegotiation in the server, and sockets inherited by the programs a process runs. Three behaviour changes: `serve_static()` no longer serves dotfiles by default and synchronous WebSocket calls throw where they would spin (under Changed), and the header setters refuse an invalid name or value (under Security). ### Added

- `headers::has_refused_header()`: whether a setter of the message refused a header (see Security).
- `static_options::dotfiles`, with the values of Express's `serve-static`: `http::dotfiles_policy::ignore` (the default), `allow` and `deny`. A dotfile path has a segment of its percent-decoded path under the prefix that is longer than one character and starts with `.`, other than `.well-known`, which is always served (RFC 8615). See Changed.

### Changed

- **Behavior change:** `serve_static()` no longer serves dotfiles (`.env`, `.git/config`, `.htpasswd`) by default. They are answered as paths without a file: with the root fallback (`index.html` by default), or `404` without one, as Express's `serve-static` ignores them. `.dotfiles = http::dotfiles_policy::deny` answers them `403`; `.dotfiles = http::dotfiles_policy::allow` serves them as 0.9.1 did. The check reads the request path only (it adds no filesystem call), so dot segments in the configured directory itself do not count.
- **Behavior change:** the synchronous calls of `websocket_client` and `http::client` no longer run an io_context where they would spin a worker, re-enter handlers or run another thread's io_context (see Fixed). This changes only code that already misbehaved that way:
  - the synchronous calls of `websocket_client` made on an `async_client` worker or in its callbacks, or in an `executor_client` coroutine, now throw `std::logic_error` (`close()` included, which leaves the connection open);
  - called from another thread on a WebSocket of `async_client` or `executor_client`, they need something running its io_context (started workers, a thread running the `executor_client`'s io_context), or they wait until something does;
  - a synchronous call of `http::client` re-entered from one of its own callbacks throws.

  Replacements: the coroutine API (`send_text_async()`, `send_binary_async()`, `receive_async()`, `close_async()`, from a coroutine callback `-> awaitable<void>` or `async_client::run()`), `run()` with `on_message()`, and `stop()` to close without waiting.
- 0.9.2 keeps the API of 0.9.1 and the SONAME `libthinger_http.so.0.9`, with the same class sizes, but not every layout: `headers` has a new protected member, which moves two of its members and two private members of `http_request`; `static_options` has a new public member (see Added) and `websocket_client` a new private one; and `http_client_base` has a new protected virtual function, which moves the destructor in the virtual table of every client. Code built against the 0.9.1 headers must be rebuilt against 0.9.2.

### Fixed

- The synchronous calls of `websocket_client` (`send_text()`, `send_binary()`, `receive()`, `close()`, and `set_keepalive()` off the executor of the WebSocket) no longer run an io_context they do not own. In 0.9.1, called on an `async_client` worker (e.g. in a `client.websocket(url, callback)` callback, as the README showed), they looped `poll_one()`: the worker spun at 100 % CPU and ran other connections' handlers inside the callback. Called from any other thread, they ran the worker's io_context from a second thread. Now, on a thread running the io_context of the WebSocket (a worker, so its callbacks, a coroutine of `executor_client`, a strand of either), they throw `std::logic_error` before starting anything, as they already did on a strand, with a message naming the call, the coroutine API and `stop()`. On any other thread they wait for the operation while the threads of the WebSocket run it, as a blocking call does in Go. A WebSocket of `http::client`, whose io_context only its synchronous calls run, still waits by running it, as before. See Changed.
- The synchronous calls of `http::client` throw `std::logic_error` when made within one of its own callbacks (e.g. a `send_streaming` callback), where they ran its io_context re-entrantly, and `asio::run_until()` throws instead of polling when called on a thread running its io_context.
- `asio::io_context_of()` also finds the io_context behind a work-tracked io_context executor; the reverse proxy uses it instead of a private copy.
- The README examples "WebSocket Client (Async Callback)" and "Event-Driven", the async WebSocket example and the doc comments use the coroutine API, `run()` and `stop()` in `async_client` callbacks, and no longer claim thread-safe sends for `websocket_client`.
- The WebSocket message interface delivers the frames a client sends right after its upgrade request, without waiting for the `101`, as the stream interface (`upgrade_websocket_stream()`) already did and as Node's `ws` and Go's gorilla/websocket do. 0.9.1 logged a warning and closed the connection. They are read first, once the connection starts reading (not while it is paused), and go through the same checks as any other frame (1002, 1007, 1009).
- `send_file(path, true)` writes `Content-Disposition` as Express's `content-disposition` package does (RFC 6266): the ASCII `filename="…"` has `"` and `\` escaped, and each character outside printable ASCII written as `?`; `filename*=UTF-8''…` (RFC 8187) is added, percent-encoded, when the name has bytes outside printable ASCII or reads as percent-encoded (`%` and two hex digits). A printable ASCII name without `"`, `\` or such a `%XX` gets the same header as before. 0.9.1 wrote the file name as it was, so a name with a quote or a non-ASCII character reached browsers cut or garbled.
- Concurrent `stop()` calls on a standalone `http::server` (from a signal handler and the application, or from two threads) no longer race: one atomic exchange decides which call stops the server, and the others return at once. Before, two calls could both pass the check and reset the server's work guard at the same time. A caller that needs the server stopped still waits on `wait()`.
- More log lines a peer can trigger at will are logged at debug level, with the same text, as 0.9.1 did for the others: a WebSocket message larger than `max_message_size`, a text message that is not valid UTF-8, a connection refused by the listener's allowed or forbidden remotes, and a failed TLS handshake. The WebSocket lines were errors, the other two warnings; any peer, a scanner included, can cause them.
- The sockets of the library are close-on-exec, so the programs its process runs (fork and exec) no longer inherit them: the client's connections (`tcp_socket::connect()`, so TLS too, and `unix_socket::connect()`), set once connected, and the listening sockets, set once opened. Accepted connections already were. asio opens sockets without `SOCK_CLOEXEC` (Go and libuv open every descriptor with it), and a child launcher that closes the descriptors it does not need with `close_range()` (Boost.Process v2) cannot on Linux kernels before 5.9, so each program a client application ran held its connections open (and a server's port stayed bound while a program it ran lived on). A program forked by another thread in the instant between the opening of a socket and the end of its connect, or its opening for a listening socket, may still inherit it.

### Security

- A WebSocket connection of the message interface (`res.upgrade_websocket()`) takes memory as payload bytes arrive, and gives it back after a large message:
  - A frame header no longer makes the server reserve the payload it announces. The read buffer of a connection grows as payload bytes arrive, at most doubling what it holds per read and starting at 1 KiB, as `read_body()` does since 0.9.1 and as Node's `ws` and Go's gorilla/websocket do. In 0.9.1 the whole announced length, up to `max_message_size` (16 MiB by default), was allocated and zero-filled when the header was read, so a header and one byte held 16 MiB per connection: 64 such connections now grow the process by under 16 MiB (about 1 GiB before). A frame, or the frames of a message, above `max_message_size` is still closed with 1009 when its header is read, and messages are delivered as before.
  - The connection gives up its read buffer after delivering a message above 64 KiB, so connections that each received one large message no longer keep its size until they close: 64 connections that received one 4 MiB message each keep under 8 MiB (at least 256 MiB before). Messages up to 64 KiB reuse the same buffer, with no allocation per message.
- **Behavior change:** header names and values set by the application are checked when they are set, as Node's `setHeader` and Go's `net/http` check them. A name that is not a token, or a value with CR, LF, NUL or another control character but HTAB (RFC 9110, section 5), is refused by `add_header()`, `set_header()`, `set()`, `add_proxy()`, `set_proxy()`, `response::header()` and the setters built on them: it is not stored (a refused `set_header()` leaves the previous value), a debug line names it without its value, and `has_refused_header()` is set. Nothing throws, and no signature changes. Valid values, HTAB and bytes 0x80–0xFF included, are sent byte for byte as before. Parsed headers, already checked by the parser, and the values the library builds itself are not checked again, so parsing and serializing cost the same.
  - A response is sent without the refused header, as Go's server drops an invalid field. The reverse proxy still answers with an error when one of its hooks sets an invalid header.
  - A client request with a refused header fails before any connection is opened or taken from the pool, as Go's client does: `send()` and the verb helpers return `boost::asio::error::invalid_argument`, as for a URL the client cannot parse, `send_streaming()` returns an error, `upgrade_websocket()` returns no WebSocket, and the callbacks of `async_client` get the failure.
- `response::redirect()` writes each byte of its target that a header value cannot hold (CR, LF, NUL and the other control characters but HTAB) as `%XX`, as Express's `res.location()` does, so the redirect is still sent. Other targets are sent as before, spaces, `%` and non-ASCII bytes included.
- A route parameter regex that the route tree cannot compile (a group as `(ab|cd)+`, or a regex matched on the whole path as `\w+\b`) is no longer run through `std::regex` on a text over 2048 bytes: such a text does not match that route, and the request goes on to the other routes, the not-found handler or `404`/`405`, as a path no route matches. libstdc++ matches recursively, about one frame per byte, so a request target of up to 16 KiB on such a route could overflow the stack of the thread serving it, as 0.9.1 prevented for the Host name. Static segments, parameters, compiled character classes, word alternatives and catch-alls still match paths of any length, with no extra work.
- The TLS server contexts the certificate manager creates (from a PEM certificate, and its self-signed default) refuse renegotiation (`SSL_OP_NO_RENEGOTIATION`, where OpenSSL defines it, since 1.1.0h): a TLS 1.2 client that asks to renegotiate gets an alert, as Go's servers never renegotiate. It matters on OpenSSL 1.1.1, which otherwise allows client-initiated renegotiation; TLS 1.3 has none. Contexts passed in ready-made keep their own options.

Node and Go reject a missing `Host` too, and Go a repeated one. HTTP/1.1 clients that omit `Host` must send it; an HTTP/1.0 request may still omit it, and an empty `Host:` is still accepted (served by the default host). Requests passed to `dispatch()` are not checked. The reverse proxy sends a `Host` to its target in every case (see Fixed).

Code built against the 0.9.0 headers must be rebuilt against 0.9.1.

### Removed

- `thinger/http/data/out_sendfile.hpp` and `thinger/http/data/out_buffer.hpp`, left over from the callback API of the sockets (`out_sendfile.hpp` overrode a callback `to_socket()` that no longer exists, so it did not compile) and included by no file. The install rules of `CMakeLists.txt` are commented out, so no installed set of headers shipped them.

### Fixed

- The idle timeout no longer closes a connection while the handler of its request runs, once the request was received whole: a handler longer than `idle_timeout`, on a route without `.timeout()`, gets its response to the client, as the README said and as Node and Go do. The header, request and write deadlines apply as before, and a body still arriving keeps moving the idle deadline, so a client that goes silent mid-body is still closed with every request deadline off. A handler that returned without answering (to answer later from a copy of the response) is still idle-timed unless its route sets `.timeout()`.
- A keep-alive response whose write fails closes the connection, as Go and Node do, so the requests a gone client pipelined behind it are not handled.
- Request header fields accept optional whitespace around their value, as RFC 9112 section 5.1 allows and Node, Go and Beast do: `Name:value`, `Name:` (an empty value), `Name:\tvalue`, several spaces after the colon, trailing spaces and tabs, and tabs inside the value. 0.9.0 answered all of them with `400`, which refused hand-written HTTP clients of devices. The whitespace around the value is not part of it: `Content-Length: 5 ` frames a 5-byte body and `Transfer-Encoding:\tchunked` a chunked one, while `Content-Length` and `Transfer-Encoding` stay as strict as before on the trimmed value. Whitespace between a field name and its colon, folded lines and control characters other than the tab are still `400`.
- A request target is refused for `..` only when it is a segment of the percent-decoded path (`/..`, `/a/../b`, `/%2E%2E/x`, `/a%2F..%2Fb`); the path ends at the first `?` as sent. 0.9.0 refused any `..` in the target, query included, so `/api/items?range=1..5` and `/files/v1..v2.txt` got `400`; they are now served, also by `serve_static()`.
- `+` is literal in the path of a request, as in Node's `URL.pathname` and Go's `URL.Path`: `GET /a+b` has the resource `/a+b`, not `/a b`, and `serve_static()` looks for `a+b`. Query parameters and form bodies still decode `+` as a space, and `util::url::url_decode()` is unchanged.
- `serve_static()` percent-decodes the path under its prefix: `/static/my%20file.png` serves `my file.png` and UTF-8 names are found. A decoded `%2F` separates directories, and a malformed escape or a decoded NUL gets `400`; a decoded path resolving outside the directory still gets `403`. 0.9.0 looked for the encoded name, so such files got `404` or the fallback. Path parameters of other routes stay raw, as before.
- Static files (`serve_static()` and `res.send_file()`) with a body over 1 MiB, ranges and precompressed siblings included, are streamed in 64 KiB pieces, each read once the previous one is written, so a response holds about one piece whatever the size of the file and the pace of the client; a client that stops reading is closed by `write_timeout`. 0.9.0 read the whole file into memory on the IO thread for every request, so memory grew with the number of downloads times the size of the file. Bodies up to 1 MiB are read whole, as before. Text files over 4 MiB are no longer compressed on the fly (it needs the whole body): they are sent as they are, without `Vary`, or as their precompressed sibling. See [Static Files](README.md#static-files).
- `http_request::set_host()` splits a bracketed IPv6 literal after its `]`: `[::1]:8080` gives the host `[::1]` and the port `8080` (0.9.0 split it at the first `:`). The brackets stay in the host, as WHATWG `URL.host` does; a value starting with `[` without a `]` right before its `:` is the host whole.
- The reverse proxy always sends a `Host` field to the target, empty when it preserves the host of a request that had none (an HTTP/1.0 request may omit it), so the target does not answer `400` for a missing `Host`.
- The client follows relative redirects. A `Location` without a scheme (`/login`, `login`, `../x`, `?q=1`, `//host:port/path`) is resolved against the URL of the request that got it, as RFC 3986 §5.2 says and as Node's `fetch` and Go's `http.Client` do, with `.` and `..` segments removed (a `..` above the root stops there). It was sent with no host. A `Location` that keeps the host keeps the request's Unix socket, and `Authorization` follows only when the resolved URL has the same origin.
- A redirect to a `Location` the client cannot parse (another scheme such as `ftp:`, an invalid one, a host it does not support, a URL over the length cap of Security) ends the chain with `boost::asio::error::invalid_argument`, as Go and Node do, with the 3xx response attached so its status and headers stay readable. No further request is sent. A 3xx with an empty `Location` is returned as a response, as one without it already was.
- The client follows a `303 See Other` with a GET and no body, as RFC 9110 §15.4.4 says and as Node and Go do, and `client_response::is_redirect()` is true for it. It was returned as a final response.
- A 307 or 308 redirect of a request with a body sends one `Content-Length`. It sent two, which llhttp (Node) rejects with 400.
- Log lines a peer can trigger at will are logged at debug level, as the listener already logs failed handshakes, with the same text: an invalid request or a header section too large, a request with invalid body framing, a route timeout (`Request timed out`), a congested WebSocket discarding messages, and a WebSocket protocol error. They were errors and warnings any client could write as often as it liked.

### Security

- A client that pipelines requests and never reads the responses can no longer make the server build and hold every response in memory. The server stops reading the next request of a connection while 16 responses are queued on it, or while the write of its front response waits for the socket, and goes on as soon as a response is written out, losing no request (Node pauses its parser the same way; Go reads one request at a time). A paused connection stays bounded by its write deadline, otherwise by its idle deadline, and ends on close, client reset, `stop()` and `shutdown()`. When the client reads, the cost is one branch per request, with no allocation, timer or coroutine.
- A request body with a `Content-Length` takes memory as its bytes arrive, not when its head arrives: `read_body()` reserves 64 KiB first, then grows geometrically up to the announced length, as Go's `io.ReadAll` does. In 0.9.0 the whole announced length was allocated and zero-filled before any byte arrived, so a head alone announcing 8 MiB committed 8 MiB until the request deadline: 64 such heads now grow the process by under 32 MiB (about 512 MiB before). The limit check still comes before any allocation, and a body under 64 KiB is still one allocation.
- A `std::regex` no longer runs on a host name or a URL of any length a peer sends: libstdc++'s matcher recurses about once per byte, so one value of some kilobytes could overflow the stack and crash the process.
  - Server: a `Host` longer than any DNS name (253 bytes, without its port and one trailing dot) is no longer matched against the pattern virtual hosts (`host("*.example.com")`, `:name` hosts and `host_regex()`): it is served by the default host, as any name no virtual host matches. Exact hosts are still found by their name. See [Virtual Hosts](README.md#virtual-hosts).
  - Client: a URL longer than 8192 bytes is refused before it is matched, in `http_request::set_url` and in `websocket_util::parse_websocket_url`; a hostile server's `Location` can reach 16 KiB. A URL given by the caller is capped too: a request to a longer one fails with no request sent.

## [0.9.0] - 2026-11-01

Configuration and request lifecycle: the certificate manager and the workers are objects the application owns, one server serves HTTP and HTTPS, the connection settings are per server, a shutdown has one deadline, `stop()` closes what is open, request cancellation is cooperative and opt-in per route, and server connections, event streams and proxy tunnels have deadlines by default. Breaking, with no deprecation wrappers: see [Migrating from 0.8 to 0.9](MIGRATING.md#from-08-to-09) for the changes below in migration order, with code before and after, and the behaviour changes B1–B11 under Changed.

### Added

- `asio::async_event` (`asio/async_event.hpp`): a signal coroutines wait on. `set()` wakes every waiter and stays set until `reset()`; `wait()` returns `true` once set, and `false` when the wait is cancelled (through `||`, `with_timeout()` or its cancellation slot) or the event is destroyed. It belongs to the executor it is given, as the object that owns it: signal it from another thread by dispatching there. Destroying its io_context with waits pending destroys them, unresumed, as it destroys a pending timer's (a coroutine waiting on an event of an object it keeps alive is freed with the io_context), and an event, like a timer, does not outlive its io_context. The library uses it for every signal between coroutines, which were timers set to `time_point::max()` and cancelled.
- `asio::watchdog` (`asio/watchdog.hpp`): a deadline that activity moves, with one timer checked when it expires. `expires_at()` re-arms the timer only for an earlier deadline, `hold_until()` keeps it from expiring before a time, and `cancel()` stops it. The callback runs from the timer, never inside a call, and never after `cancel()` or the destruction of the watchdog, which it may destroy; it should hold its owner weakly. The WebSocket and SSE keep-alives, the write timeout of their queues (`write_flow`), the connection timeout and deadlines of the server and the idle timeout of a `socket_pipe` use it, in place of generation counters and the connection's own deadline.
- `certificate_manager::remove_default_certificate()`: the manager has no default certificate, and `get_default_certificate()` returns none (no self-signed one is generated) until `set_default_certificate()` sets one again. Servers already listening keep the context they listen with; a server that starts listening afterwards with that manager fails, with an error logged. Thread-safe, as the other setters.
- `asio::listener` (`asio/listener.hpp`), with `listener_options` and `executor_provider` (`std::function<boost::asio::any_io_executor()>`): one type that accepts plain TCP, TLS and Unix domain connections, in place of the socket servers (see Removed). `listener(options, accept_on, serve_on)`; `open()` resolves the host (synchronously), binds and listens, returning an `error_code`; `start(on_connection)` accepts, handing each connection to the handler on the next `serve_on` executor, a TLS one once its handshake succeeded; `stop()`; `local_port()`; `url()` (`"http://0.0.0.0:8080"`, `"https://[::1]:443"`, `"unix:/run/x.sock"`). A listener is used once: an `open()` after one that succeeded (or after `stop()`) returns `already_open`, while one that failed (e.g. the port busy once `max_listening_attempts` ran out) may be retried, and opens with TLS as the first would have. `stop()` may be called from any thread, the handler included, and more than once: it closes the listening socket and the connections whose handshake is pending or waiting for a slot, and once it returns no handler starts and none runs on another thread (it waits for those). The destructor stops it. The executor providers are called outside the listener's lock, so a provider may call back into the listener (`url()`, `local_port()`), and one that blocks holds up neither the accepts nor `stop()`; no connection is accepted after `stop()`, and none handed over once it returned. The executors must run on an `io_context` in this release (`open()` returns `invalid_argument` otherwise). `listener_options` holds what the setters of the socket servers set: `endpoint` (`tcp_endpoint{host, port}` or `unix_endpoint{path}`), `tls` (a `certificate_manager`; null for plain connections), `client_verify`, `handshake_timeout` (60 s; 0: none), `tcp_no_delay` (true), `max_listening_attempts` (-1: until it binds, every 5 s), `allowed_remotes` and `forbidden_remotes`, and two new options (below). See [Listeners](README.md#listeners).
- `listener_options::max_pending_handshakes`: the TLS handshakes in progress at once per IO thread (per serve executor); 0, the default, is unbounded. A connection whose thread is at the bound waits for a slot before its handshake starts, accepting goes on meanwhile, and the wait counts against `handshake_timeout`: a connection still waiting when it expires is closed, without reaching the handler. See [Handshake Deadline](README.md#handshake-deadline).
- `listener_options::session_cache` (`asio::session_cache_options`, in `asio/ssl/tls_session.hpp`, next to `client_verify_options`; `listener.hpp` includes it): `enabled` (true) and `size` (20,480 sessions, OpenSSL's default), applied to every context of the listener's manager, those it creates or is given later included. Disabled, no session is resumed: no server cache and no tickets, in TLS 1.2 and 1.3. Listeners sharing a manager must agree: `open()` returns `invalid_argument` and binds nothing when its cache differs from the one an open listener of the same manager applied, or when it is enabled with a `size` of 0. Once those listeners stopped, a new one may apply another. See [Session Cache](README.md#session-cache).
- `server_base::listen(asio::listener_options)` (`http::server`, `http::pool_server`): opens a listener for the options (plain TCP, TLS when `tls` holds a `certificate_manager`, or a Unix socket) and serves the application on it, returning an `error_code`. It may be called several times, each call opening a listener of its own: one server serves HTTP and HTTPS, and a Unix socket, with one application (see Changed). See [Listeners](README.md#listeners).
- `server_base::listening_on()`: where the server listens, one entry per listener open, in the order they opened (`"http://0.0.0.0:8080"`, `"https://[::1]:8443"`, `"unix:/run/x.sock"`), with the port the system chose for a port 0; empty while it does not listen. It replaces `local_port()` (see Removed).
- `http::connection_options` (`http/server/server_base.hpp`) and `server_base::set_connection_options(options)`: how the connections of a server are served, per server: `idle_timeout` (120 s), `linger_max_bytes` (8 MiB) and `linger_timeout` (5000 ms) of the lingering close, `logging` (a `body_logging`, off), and three deadlines, as `std::chrono::milliseconds`, 0 disabling each: `header_timeout` (60 s, Node's `headersTimeout`), `request_timeout` (300 s, Node's `requestTimeout`) and `write_timeout` (60 s, nginx's `send_timeout`). Copied once, and read by every connection the server accepts afterwards (a call after `listen()` never changes the connections open). Two servers of one process may set different values. See [Connection Options](README.md#connection-options).
  - A request counts from its first byte (the first one of a connection, from the start of serving it; a pipelined one, from the start of parsing it). A head not complete within `header_timeout` (capped by `request_timeout`) is answered `408 Request Timeout` with `Connection: close` and the connection closed at once; a connection that sent no byte of its first request is closed without a response.
  - A request whose body was not read to its end within `request_timeout` has its scope cancelled with `cancel_reason::timeout` and its pending body read failed, and is answered `408` with `Connection: close`, the connection closing gracefully after it, as Node does; if its response started, or an earlier one is still being written, the connection is closed instead. What its handler reads or writes afterwards fails on the closed connection.
  - A response write of which the socket accepts no 64 KiB slice (the whole write, if smaller) for `write_timeout` closes the connection, kept alive or not, and `idle_timeout` never cuts a response being written; the client taking bytes from the socket is not checked, so a slow client with a large send buffer may be cut while it still reads.
  - The three run on the connection's existing watchdog: no timer, coroutine or allocation per request. They are on by default (B9 in Changed).
- `request::connection()` returns a `connection_info` (`http/server/http_stream.hpp`): `peer_ip`, `peer_port` and `local_port` (strings, as the socket gives them) and `secure` (TLS) of the connection the request came from; for a request dispatched in memory, the `peer_ip` of the dispatch (`dispatch_options::remote_ip`), not secure; empty once the connection is gone. `request::tls()` returns the `asio::tls_session` of the connection (the client certificate of an mTLS route in `peer_chain_der`), `std::nullopt` without TLS, in memory or once the connection is gone. They replace `get_socket()` and `get_http_connection()` (see Removed).
- `asio::workers::next_executor()`: the executor of the next thread of the pool (round-robin), from any thread, without a lock (an atomic counter over a table published by `start()`); a null executor when the workers do not run. `provider()` returns it as a callable, the `executor_provider` of a listener. See [Workers](README.md#workers).
- `awaitable<bool> server_base::shutdown(std::chrono::steady_clock::time_point by)`: the graceful shutdown with one absolute deadline, `by`, which is its whole budget. It stops listening, calls `on_shutdown()` and tells the connections taken over, closes the idle ones, and lets those handling a request finish until `by`. At `by` it closes what is still open and returns `false`, without waiting for the handlers still running; it returns `true` once every connection finished, at once for a server with none open. It may be awaited from any executor, a thread of the server included (a handler, a worker of a `pool_server`), which it does not block. Several calls, concurrent ones too, share one end and one result, and the first sets `by`. Workers stopped meanwhile (`workers.stop()` on another thread, or on the worker awaiting it) make it end by `by`, without an exception. It replaces `begin_shutdown()` (see Changed). See [Shutdown](README.md#shutdown).
- `server_base::stop_listening()` is public: it closes every listener, so new connections are refused, and leaves the connections open serving (`stats()` still counts them); later calls do nothing. It was private, and returned whether the server listened. With `shutdown()` and `stop()` it makes the three steps of stopping a server: quiesce, drain, release. It is the call to stop accepting while the connections open finish, which `stop()` no longer is: `stop()` closes them (B10 in Changed).
- The cancellation scope of a request: cooperative, and opt-in per route (see B2–B5 in Changed). Each request has one, which the library cancels once, for the first reason that comes, a `cancel_reason` (`http/server/request.hpp`): `client_gone` (the client reset the connection, a read or write on it failed, or it ended before the request was complete), `timeout` (of the route, or of the in-memory dispatch) or `shutdown` (the drain deadline reached with the request in progress); `none` until then. The handler goes on unless its route declared the reason, and always at the drain deadline. See [Cancellation](README.md#cancellation).
- `route::cancel_on(std::initializer_list<cancel_reason>)`: the reasons for which the library interrupts the handler of the route, whose awaits then end with `operation_aborted` (asio cancels its coroutine). None by default; `none` is ignored, so `cancel_on({})` keeps the default. `get_cancel_on()` returns them as bits `1 << reason`. Groups do not carry it: set it on each route.
- `route::request_timeout(duration)`, `route_group::request_timeout(duration)` and `virtual_host::request_timeout(duration)` (with `get_request_timeout()` on routes and hosts), next to the body limits and the timeout of a route: the request deadline of their requests instead of `connection_options::request_timeout`, e.g. longer, or 0 for none, for routes receiving large uploads. Precedence route > group > host > connection, measured from the start of the request; a host's applies to its not-found handler. See [Limits and Timeouts per Route](README.md#limits-and-timeouts-per-route).
- `request::cancelled()`: the reason the scope was cancelled, `none` until then (and for a request built without a stream), from any thread. `awaitable<cancel_reason> request::client_gone()`: completes once the scope is cancelled, whatever the reason, and returns it (`none` if the wait itself is cancelled, e.g. by `||`); it never completes if the scope is never cancelled. `request::cancellation_slot()`: a slot cancelled (terminal) with the scope while the handler runs, to bind with `boost::asio::bind_cancellation_slot` to the awaits a handler of a default route can abandon, one at a time (asio's rule); not connected for a request without a stream. Await `client_gone()` and bind the slot on the executor of the handler.
- `http::sse_event` (`http/server/sse_connection.hpp`), an SSE event as one value: `event`, `id` and `retry` (`std::optional`s) and `data`, written in that order, each line of `data` a data field of its own, then the empty line that dispatches it, as `send_event()`, `send_id()`, `send_retry()` and `send_data()` write them, and refused as they are (an event type or ID with a CR or LF, an ID with NUL), and a negative `retry` too. Sent with two new methods of `sse_connection`: `bool send(const sse_event&)` queues it without waiting (false if refused, an error logged), and `awaitable<bool> send_async(sse_event)` waits until it is written: `true`, or `false` if refused or once the connection closed or failed first; the overflow policy never drops it, and a cancelled wait leaves it queued (as `websocket_connection::send_text_async()`).
- `sse_connection::send_comment(comment)`: a comment (`: comment`, a line the client ignores) queued with the event that follows, so `drop_oldest` drops them together; refused (false, an error logged) if it holds a CR or LF.
- `sse_connection` runs on an executor of its own, which may be a strand: the constructor takes it, `sse_connection(socket, executor = {})` (by default the executor of the io_context of the socket, as before), `get_executor()` returns it, and `execute(callback)` runs a callback there (at once when already there), as on `websocket_connection`. Its writes, keep-alive, callbacks (`on_close()`, the watermarks) and read loop run there; `start()`, as the `send*()` methods and `stop()`, may now be called from any thread.
- `websocket_connection::get_executor()`: the executor of the WebSocket (the one of its socket), where its callbacks run.
- `thinger/http/server/upgrade.hpp`, the types of the upgrades, light (it declares the connection types and includes none): `response.hpp` and `http_server.hpp` include it. It holds `server_scope`, `upgraded_connection`, `upgraded_websocket`, `websocket_accept_options` and `sse_options` (below), the handler types `takeover_handler` and `takeover_coroutine` (from `http_stream.hpp`), and `websocket_handler`, `websocket_coroutine`, `websocket_stream_handler`, `websocket_stream_coroutine`, `sse_handler` and `sse_coroutine` (from `response.hpp`). See [Taking Over the Connection](README.md#taking-over-the-connection).
- `http::server_scope`: the link between a connection taken over (or upgraded) and the server it came from, a handle whose copies share it. `set_type(connection_type)` sets what the connection counts as in `stats()`; `on_shutdown(callback)` asks to be told once, on the io_context of the socket, when a shutdown starts its drain (released before it is called, so it may own the socket; what it throws is logged); `closed()` says the owner closed it: it no longer counts and is not told, and calling it again does nothing. It holds the server weakly: with no server (default-constructed, or a socket that does not come from one) or once the server is destroyed, its methods do nothing. The server counts the connection while the socket handed out lives (its copies, and a WebSocket built on it, included) or until `closed()`, and closes what is still open at the shutdown deadline, as it did with the socket attachment (see Removed).
- `http::upgraded_connection` (`socket`, `buffered`, `scope`), what a `take_over()` handler receives, and `http::upgraded_websocket` (`stream`, the `std::shared_ptr<asio::websocket>` it received before, `protocol` and `scope`), what an `upgrade_websocket_stream()` handler receives (see Changed).
- `http::websocket_accept_options`, the options of both WebSocket upgrades (see Changed): `protocols`, `protocol_required` (`true`) and `binary` (`true`, for the byte stream) as in `websocket_options`, and `max_message_size` (16 MiB), `ping_interval` and `idle_timeout`, which configure the message interface too: its largest message (at least 1 byte; a larger one closes with 1009) and its keepalive, both fixed until now. `ping_interval` and `idle_timeout` are `std::optional<std::chrono::milliseconds>`: unset is the default of the upgrade (60 s and 120 s with the message interface, off as a byte stream), `0` turns each off. `protocol_required = false` now applies to `upgrade_websocket()` too: a client offering no subprotocol is accepted without one.
- `http::sse_options`, the options of `start_sse()`: `keepalive`, the interval of the keep-alive comments (15 s; 0: none), which `sse_connection::set_keepalive()` still changes later.
- `websocket_connection(socket, const websocket_accept_options& options = {}, server_scope scope = {})` and `sse_connection(socket, executor = {}, server_scope scope = {})`: parameters added with defaults, so the constructors called as before compile and behave as before (16 MiB, 60/120 s, not tracked), but for the write timeout of their queues (B11 in Changed). The upgrades pass the options and the scope of the connection: a connection built with a scope counts as a `websocket` or an `sse` connection, is told of a shutdown through it (`on_shutdown()`, a WebSocket closing with 1001), and stops counting once closed.
- `websocket_client::set_keepalive(ping_interval, idle_timeout)`, with `get_ping_interval()` and `get_idle_timeout()`: the keepalive of a client WebSocket (see Changed), changed without `release_socket()`; `(0, 0)` turns it off. `websocket_client::get_close_code()`: the status code of its closing handshake (1001 when the keepalive closed it).
- `asio::run_until(io_context, done)`: runs an `io_context` on the calling thread until `done()` holds, then what is ready, without waiting for it to run out of work; the synchronous calls of `http::client` and `websocket_client` wait with it.
- `websocket_util::accept_key(key)`: the `Sec-WebSocket-Accept` value answering a `Sec-WebSocket-Key` (RFC 6455 section 4.2.2), which `validate_accept_key()` now compares with.
- `http_response::status::misdirected_request` (421, "Misdirected Request"), with what the server checks before answering it (see Security): `request::misdirected()`, whether the request came on a TLS connection whose handshake (SNI) chose another client certificate mode or certificate than its `Host` gets, so that it must not be served there (`false` without TLS, in memory or once the connection is gone); the virtual `asio::socket::misdirected(host)` behind it, `false` by default and answered by `ssl_socket`; and `asio::tls_handshake_record` (`certificate_manager.hpp`), what the handshake of a server connection chose (the SNI name, the mode applied and the listener's, the manager), with its `misdirected(host)`. A socket class of the application compiles unchanged.
- `virtual_host::host_name(host)`: the host name of a `Host` value in its own case, without port nor trailing dot and without a copy (a view of `host`), beside `normalize_host()`, which lowercases it into a string.
- `proxy_options::tunnel_idle_timeout` (120 s, `proxy_options::DEFAULT_TUNNEL_IDLE_TIMEOUT`; 0 disables it): a reverse proxy tunnel with nothing forwarded in either direction for that long has its connections to the client and to the target closed. Any byte forwarded counts, so WebSocket data, pings and pongs keep it open, with traffic in one direction too; a byte counts once written to the other side, so a peer that stops reading ends it, as do the bytes sent right after the handshake when their peer never reads them. Separate from `idle_timeout`, which covers the exchange only, and set per `forward()` call like the other options. A `static_assert` keeps the default above the 60 s after which a thinger-http WebSocket pings a quiet peer. On by default (B11 in Changed). See [Reverse Proxy](README.md#reverse-proxy).
- `asio::socket_pipe::set_idle_timeout(timeout)`, before `run()`: the pipe ends as `cancel()` ends it, both sockets closed and the on-end callback called once, once nothing was forwarded in either direction for `timeout`. Off by default, as before. Each write moves one timer lazily, without a timer operation per chunk, so a pipe with a deadline runs on an io_context run by one thread or on a strand. See [Tunnels](README.md#tunnels).
- `asio::socket::send_backlog()`: the bytes written that the peer has not taken yet (`SIOCOUTQ` on Linux, `SO_NWRITE` on macOS, for TCP, TLS and Unix sockets and the WebSockets over them); 0 by default, for sockets that cannot tell. The write timeout of SSE and WebSocket connections counts its fall as progress.
- `asio::socket::write_slices(buffers, progress)`: a write in slices of `socket::WRITE_SLICE_SIZE` (64 KiB, a socket buffer), calling `progress` after each one, so that a write deadline it moves tells a slow peer that keeps reading from one that stopped, as nginx's `send_timeout` does; `buffers` is left with what was not written, and the static `socket::consume(buffers, size)` drops the bytes written from them. `asio::websocket::write_message(data, progress)` writes one message the same way, a frame over 64 KiB in slices (still one frame). The write deadlines of the server's responses and of its SSE and WebSocket connections use them.
- Tests: a hostile-peer fixture (`tests/fixtures/hostile_peer.hpp`) plays a peer that stays silent, trickles one byte at a time or does not read, from a chosen point of the exchange (after the accept, the TLS handshake, the request head, the response headers or a 101), over TCP, TLS and a Unix socket, and a peer that never accepts (its queue full). `hostile_peer_test.cpp` runs every client operation that waits on the peer against it, asserting the outcome and that it arrives at its deadline: the connect and the TLS handshake (directly, through a WebSocket and through the HTTP client); with the HTTP client, the request write, the response head and body reads and the WebSocket upgrade; and with a client WebSocket, a read from a silent peer and from a trickling one once it stops, and a write the peer does not read, which end at the idle timeout set with `websocket_client::set_keepalive()`, closed with 1001. The pending-connect case of `socket_connect_timeout_test.cpp` uses that peer, with a backlog of 1: macOS takes a backlog of 0 as the largest one, so the case never left a connect pending there. Its server-role counterpart, `hostile_client` in the same header, is a client reaching a server through a `transport_endpoint` (tcp, tls with the matrix CA, unix) that stays silent, trickles a head, sends a head then trickles its body, or sends a request and never reads, with a configurable period; four `[matrix][hostile_peer]` cases run it against the server's deadlines on every transport: silent, trickled head, trickled body and a response not read.

### Changed

- **Breaking:** `certificate_manager` is an object the application creates and owns, with `std::make_shared<asio::certificate_manager>()` (it derives from `std::enable_shared_from_this`; copy and move stay deleted), as many as it needs, each with its own certificates, TLS options and client certificate modes: two servers with different managers serve different certificates for the same host name. Replace `instance().f()` with `manager->f()` on a manager you keep, and give it to a listener in `listener_options::tls`, for a server too (`server.listen(options)`). Nothing is shared between managers, the self-signed default for development included: each generates its own on first use.
- **Breaking:** the setters of `certificate_manager` return a `boost::system::error_code` instead of `bool`: `set_certificate()` (both overloads), `set_default_certificate(certificate, key)`, `set_tls_options()`, `set_client_verify()` and the deprecated `set_server_ciphers()`. **The meaning is inverted**: the error code is empty on success, so `if (ec)` means it failed where `if (ok)` meant it worked; `if (!manager->set_certificate(...))` now runs on success. A failure is `errc::invalid_argument` (an invalid PEM, a key that is not the certificate's, an empty host name, a name that is not a host name nor a wildcard, see below, options OpenSSL refuses), with the reason logged as before, and the manager keeps what it had. `remove_certificate()`, `remove_client_verify()`, `enable_legacy_protocols()` and the getters keep their types.
- **Breaking:** `certificate_manager::set_default_certificate(std::shared_ptr<ssl::context>)` returns a `boost::system::error_code` too, where it returned nothing: empty on success, and `invalid_argument` for a null context, with an error logged, keeping the current default certificate and whether a self-signed one is generated. `set_default_certificate(nullptr)` no longer drops the default certificate, which made the manager serve a freshly generated self-signed one (e.g. after a reload whose context failed to load): the current certificate stays. `remove_default_certificate()` (see Added) is the way to drop it, and generates no self-signed default afterwards: a call with `nullptr` meant to go back to the self-signed default has no counterpart on that manager (a new manager generates its own). Source compatible for callers that ignore the result. The PEM overload returns the result of setting the context it built.
- **Breaking:** `certificate_manager::set_certificate()`, both overloads, takes host names only: an exact name (labels of 1 to 63 letters, digits, hyphens or underscores, 253 characters at most), or `*.` followed by one. 0.8 took any name with a `.` as a regex. Any other name, a regex such as `^api\..*\.com$` included, is refused with `invalid_argument`, the reason logged as an error, and nothing changes; a name refused by the PEM overload costs no context. Names are stored lowercase, and `get_registered_hosts()` lists them as registered (`*.domain` for a wildcard). Exact names match only themselves, and a wildcard `*.domain` exactly one more label in front of `domain`, an exact name first, case-insensitively, without a regex: a lookup probes one exact name and one wildcard. The client certificate modes of `set_client_verify()` match the same way. See [The certificate manager](MIGRATING.md#the-certificate-manager).
- `certificate_manager::remove_certificate()` returns `false`, and changes nothing, when no certificate is registered with that name (a wildcard by its `*.domain`); it always returned `true`.
- The SNI callback reaches its manager through a `std::weak_ptr` kept with each context the manager creates or is given (and freed with it), no longer through the global instance. A context may now outlive its manager: once the manager is destroyed, the handshakes of a server still listening with one of its contexts stay on that context, with its certificate and its client certificate mode, whatever host name they ask for (SNI switches no certificate), without a crash. A context given ready-made to two managers takes the SNI of the last one (not supported).
- An HTTPS listener of a server takes the certificates of the manager in its `listener_options::tls`, no longer those of the global instance (a self-signed one if none was set): a manager whose default certificate was removed makes `listen()` return `invalid_argument`, with an error logged.
- **Breaking:** the socket servers are replaced by `asio::listener` (see Added and Removed). From `tcp_socket_server(host, port, acceptor_provider, connection_provider, allowed, forbidden)` and `unix_socket_server(path, ...)`: a `listener_options` with `endpoint = tcp_endpoint{host, port}` (the port a number, no longer a string) or `unix_endpoint{path}` and the filters (`std::vector`, no longer `std::set`), and two `executor_provider`s returning an executor where an `io_context_provider` returned an `io_context&` (`[&]() -> boost::asio::any_io_executor { return io.get_executor(); }`). `set_handler(h)` then `start()` (a `bool`) become `open()` (an `error_code`) then `start(h)`; `stop()` returns nothing. The setters become fields: `enable_ssl(true, verify)` and `set_ssl_context(context)` → `tls = manager` and `client_verify = verify` (a context of its own goes in the manager with `set_default_certificate(context)`), `set_handshake_timeout()` → `handshake_timeout`, `set_tcp_no_delay()` → `tcp_no_delay`, `set_max_listening_attempts()` → `max_listening_attempts`, `set_allowed_remotes()` and `set_forbidden_remotes()` → `allowed_remotes` and `forbidden_remotes`. The constructors without providers (accepting on a thread of the server and serving on the workers) have no counterpart: give the listener the workers, as `workers.provider()` (the acceptor thread stays internal, for `pool_server`). `get_service_name()` → `url()`.
- The client certificate mode of a TLS handshake, stated: a handshake that names a host (SNI) with a mode set on the manager (`set_client_verify(host, mode)`) gets that mode, stricter or weaker than the listener's (a `required` listener lets the clients of a host set to `none` in without a certificate); every other handshake (no SNI, or a name without a mode) gets the listener's `client_verify`. The connection keeps what its handshake chose, and a request on it whose `Host` gets another client certificate mode or, with SNI, another certificate entry than the SNI name is answered `421 Misdirected Request` (see Security). As in 0.8, the mode is set on each connection, so two listeners sharing a manager keep their own. `ssl_socket::set_client_verify()` is internal: only the listener calls it, until `tls_socket` (0.10).
- Trusted CAs of the client certificates that cannot be read make `open()` fail with `invalid_argument`, and nothing is bound. `tcp_socket_server::enable_ssl()` returned `false` and the server listened, accepting no connection.
- A listener holds its manager (`listener_options::tls`) from its construction until `stop()` (or its destructor), whatever `open()` returns, as a server held the context it listened with. The application need not keep a reference to the manager: one created for `options.tls` and kept nowhere else (`options.tls = std::make_shared<asio::certificate_manager>()`, as the HTTPS example does) lives as long as the listeners using it, so its per-host certificates and client certificate modes apply to every handshake until they stop, and is destroyed once the last of them stopped. A context may still outlive its manager (the application keeps it elsewhere, or a connection uses it once its listener stopped): its handshakes then stay on that context, as described above.
- **Breaking (B1):** a server serves its application on any number of listeners: one server, and one set of routes, virtual hosts, middlewares and hooks, serves HTTP and HTTPS (and Unix sockets), where an HTTPS port needed a second server with a copy of the routes. Each `listen()` opens a listener of its own, and a route (middleware, virtual host, hook) added before any request arrives, before or after `listen()`, answers on all of them; requests read them without locks, so adding one while requests are served is a data race, as `server_base.hpp` and the README say. A second `listen()` opened a single listener: `http::server` refused it (`Server already running`), and `pool_server` replaced the listener it had. `stop()`, `stop_listening()`, `shutdown()` and `is_listening()` act on every listener, and `stats()` counts the connections of all; the logs name the server by all its listeners (`server on http://0.0.0.0:8080, https://0.0.0.0:8443 stopped`).
- **Breaking:** `http_server_base` → `server_base`, and `http/server/http_server_base.hpp` → `http/server/server_base.hpp`, with no alias: `server` and `pool_server` derive from `server_base`. The umbrella header `thinger/http_server.hpp` is unchanged.
- **Breaking:** `bool listen(const std::string& host, uint16_t port)` → `boost::system::error_code listen(std::string host, uint16_t port)`, a plain TCP listener, no longer virtual. **The meaning is inverted**: the error code is empty on success, so `if (server.listen(...))` now means it failed; `if (!server.listen(...))` runs on success. The error is the listener's (`invalid_argument` for options that cannot be used, the error binding, see `listener::open()`), or `address_in_use` for an endpoint the server listens on already (the same Unix path, or the same host and port; a port 0 is always a new one), leaving that listener as it is, and for an endpoint another `listen()` is opening at the same time. It fails with `shut_down` while a shutdown is in progress, `on_shutdown()` included (and works again once the shutdown ended), and with `operation_aborted` when `stop_listening()`, `stop()` or a shutdown, called on another thread, stopped its listener while it opened (e.g. while it waited to bind again): a listener is reserved in the server before it opens, so whatever stops the listeners stops it too, and `listening_on()` lists it from the moment it accepts connections. A failed `listen()` opens nothing and leaves the listeners open as they are. The `start(host, port)` overloads keep their `bool`. See [Listeners](README.md#listeners) and [Shutdown](README.md#shutdown).
- **Breaking:** TLS is set per listener, with the manager in `listener_options::tls`: `server.enable_ssl(true); server.listen(host, port);` → `listener_options options; options.endpoint = asio::tcp_endpoint{host, port}; options.tls = manager; server.listen(options);`. `listen_unix(path)` → `listen(options)` with `options.endpoint = asio::unix_endpoint{path}`, and `set_max_listening_attempts(n)` → `listener_options::max_listening_attempts`, per listener. The other options of a listener (`client_verify`, `handshake_timeout`, `max_pending_handshakes`, `session_cache`, the remotes allowed and forbidden) are now open to the servers too.
- **Breaking:** the connection settings are per server, in `connection_options` (see Added): `set_connection_timeout(t)` → `idle_timeout`; the static `set_lingering_close(max_bytes, timeout)` of `http_server_base` and `server_connection`, which set the lingering close of every server of the process, → `linger_max_bytes` and `linger_timeout`; `log_bodies(enabled, max_length)` → `logging = {enabled, max_length}`. Set them with `set_connection_options()` before `listen()`. The process-wide values (two atomics) are gone.
- **Breaking:** `server_connection(socket)` → `server_connection(socket, std::shared_ptr<const connection_options> options = nullptr)`, the settings of its server (the defaults if null), and `start(std::chrono::seconds timeout)` → `start()`, closing it once idle for `options->idle_timeout`, or at the deadlines of `options` (B9, below). `set_body_logging()` is removed (`options->logging`).
- **Breaking (B9):** server connections have header (60 s), request (300 s) and write (60 s) deadlines by default (`connection_options`, see Added), where 0.8 had only `idle_timeout`, which every byte received moved: a client trickling one byte every 119 s held a connection through a 16 KiB head for about 22 days, and through a body for ever, and a client that stopped reading a `Connection: close` response held it for ever. A request head or body arriving slower than its deadline is now answered `408`, an upload taking over 300 s included: give such routes their own `request_timeout()` (see Added). A slow client reading a single large response frame is no longer cut by `idle_timeout` after 120 s. To keep 0.8's behaviour, set the three options to 0.
- **Breaking:** the servers listen with a `listener`. The protected API for classes deriving from `server_base` changes: `create_socket_server(host, port)` and `create_unix_socket_server(path)` → `create_listener(listener_options)`, which builds the listener on the executors of the server, with the options given to `listen()`; the virtual `listening()` is called after each listener opens (`http::server` gets its io_context ready to run on the first). The members `socket_server_`, `host_`, `port_`, `unix_path_`, `use_unix_socket_`, `ssl_enabled_`, `connection_timeout_`, `max_listening_attempts_` and `body_logging_` are gone, and the listeners are private.
- **Breaking:** `begin_shutdown(grace, on_done)` → `co_await shutdown(by)` (see Added), with `by = std::chrono::steady_clock::now() + grace`: the `bool` that `on_done` received is the result of the `co_await`. Where the caller cannot await (a synchronous handler, an `asio::signal_set` handler), `co_spawn(executor, server.shutdown(by), [](std::exception_ptr, bool clean) { ... })`. The blocking `bool shutdown(std::chrono::milliseconds grace = 30s)` keeps its name and signature, for a thread that does not serve the server (e.g. `main()`): it waits for the end of `shutdown(now + grace)` and returns its result. On a thread of the server it still does not block (it would block the drain it waits for): it logs an error, starts the shutdown and returns `false` at once; the error now points to `co_await shutdown(by)`, where it pointed to `begin_shutdown()`.
- **Breaking:** `bool stop()` → `void stop()`, on `server_base`, `server` and `pool_server` (a class overriding it changes its signature). It returned whether the server was listening (`server`: running); `is_listening()` tells it before the call.
- **Breaking (B10):** a server's `stop()` and its destructor close every connection still open, idle keep-alive ones, those handling a request and those taken over (WebSockets, event streams, tunnels), and cancel the handlers still running with `cancel_reason::shutdown`, whatever their route declared (their next cancellable await ends with `operation_aborted`), without waiting for them: each connection closes on its own thread, and what a handler sends afterwards is dropped. In 0.8 they only stopped listening, and left the connections open (see Fixed). Once they return the library touches nothing of the server: each connection, and the handler running on it, shares the routes, virtual hosts, middlewares, hooks and settings it reaches, so a handler still running may finish its current step against them; what it captured itself is the application's to keep alive. Neither waits, so both may be called from one of the server's own handlers, on one worker thread or several. The connections closed are never served again, even if the server listens again. To stop accepting while the connections open finish, call `stop_listening()`, or `shutdown(by)` for a graceful drain. See [Server Lifecycle](README.md#server-lifecycle).
- **Breaking (B8):** the end of a shutdown no longer calls the virtual `stop()`: it stops listening and releases `wait()` itself (`pool_server` and `server` set what it runs with the protected `set_shutdown_stop()`). A `stop()` overridden in a subclass of `pool_server` or `server` runs only when the application calls it, never at the end of a shutdown: what it releases after a shutdown, the subclass releases once `shutdown()` or `wait()` returned, or in its destructor. In 0.8 the end of a shutdown called it, on a worker too, while the subclass could be in its destructor.
- A shutdown has one absolute deadline, its whole budget: nothing waits past it. Once the grace period ended, it waited up to one second more for the connections left to close on their threads before stopping the server and returning, and on an `http::server` whose thread was stuck in a handler, `shutdown(grace)` never returned. Now the result, `false`, comes at `by` (within a few milliseconds): the closes are posted to the threads of the connections, and the coroutine awaiting or the thread blocked in `shutdown(grace)` decides it on its own if the threads of the server are stuck. The server stops (`wait()` returns) once those closes ran, so a thread stuck in a handler delays that, not the result; `stop()` releases `wait()` at once.
- A graceful shutdown (`shutdown(by)` and `shutdown(grace)`) ends as soon as the last connection leaves: the connection tracker tells it, where it checked the count every 10 ms and so ended up to 10 ms later. While it waits it keeps one timer, at its deadline, and no longer wakes the io_context every 10 ms. Its result, its deadline and the order at the deadline are unchanged; a connection leaving when no shutdown waits costs one atomic load more.
- `co_await shutdown(by)` works on a thread of the server, without blocking it: the other connections of that thread go on being served while it drains. In 0.8 only `begin_shutdown()` could start a shutdown there and learn its end.
- The listeners of a server drain at once, under one `by`: two listeners with a slow handler each end in the time of the slower one, not the sum. In 0.8 HTTP and HTTPS were two servers (see B1 above), shut down one after the other, each with its own grace period.
- A shutdown of an `http::server` whose `wait()` is not running its io_context (not called yet, or returned) ends at once: `true` if no connection is open. It waited for `wait()` to run the io_context, so a blocking `shutdown(grace)` waited until then.
- The log line of a shutdown starting gives the time left until `by`, in milliseconds rounded up: the grace period given to `shutdown(grace)` (`grace period of 30000 ms`, as in 0.8), and what is left of `by` for `shutdown(by)` (`0 ms` once past).
- The SSE keep-alive no longer keeps its `sse_connection` alive: the read loop does, until the client goes or the stream stops, as before. The other moves to `async_event` and `watchdog` keep the observable behaviour (timeouts, keep-alives, closes, shutdown).
- **Breaking:** `asio::workers` is an ordinary object the application creates, starts, hands by reference to what runs on it, and stops: there is no process-wide pool (`get_workers()` is removed, see Removed), and several `workers` in one process share nothing. Replace `asio::get_workers()` with a `workers` you keep (`asio::workers workers; workers.start();`), alive longer than the servers and clients on it. `pool_server()` → `explicit pool_server(asio::workers&)` and `async_client()` → `explicit async_client(asio::workers&)`, with no default constructor. `pool_server` derives only from `server_base` (`http_server_base` in 0.8, see above), without the `using http_server_base::start` that brought its `start()` overloads back. See [Workers](README.md#workers).
- **Breaking:** the workers never start or stop by themselves. They started when the first `pool_server` or `async_client` was built (unless `set_auto_manage(false)`), and stopped when the last one was destroyed; now no thread runs until the application calls `start()`, and they run until it calls `stop()` or destroys them. Start them before a `pool_server` listens or an `async_client` makes a request.
- **Breaking:** stopping the workers no longer stops the servers and clients on them. `stop()` first stopped every `pool_server` (its listening) and `async_client` (releasing its `wait()` and closing its idle connections) built on them; now the application stops or destroys them before `workers.stop()`, which stays the final bound for what is left: it stops every thread and destroys the handlers still pending. The io_contexts now live on, stopped, until the workers are destroyed, so a client destroyed after `stop()` still closes its connections on them; a `workers` started and stopped many times keeps the io_contexts of every start until then.
- **Breaking (B7):** `async_client::stop()` ends the requests in flight before returning, as the destructor does: it cancels them, their callbacks are not called (one that completed meanwhile may still call its own), and the coroutines of `run()` see their requests fail with `operation_aborted`. Cancellation reaches a request in any phase, the connect and the TLS handshake included. Called from a thread that is not one of the workers, it returns once none of them runs, nor any callback of the client (a callback running is waited for, not interrupted; a request still running 1 s after its cancellation is dropped at its next resumption); called from one of the workers, e.g. in a callback, it does not wait, and none of them resumes anymore. Requests started while it runs are not run, and their callbacks are never called; those started after it returned run as before. In 0.8 `stop()` released `wait()` and closed the idle connections, which it still does, but let the requests in flight go on. Once the destructor returns, no callback or coroutine of the client runs, wherever it was called from: a client may be destroyed from one of its own callbacks, and whatever its callbacks captured may be destroyed right after it, while the workers still run (the order [Workers](README.md#workers) documents). No signature changes. See [Async Client](README.md#async-client-async_client).
- The coroutines of `async_client::run()` run on an executor of the client that wraps their worker's and drops them once the client stopped, no longer on the worker's io_context executor: `asio::io_context_of()` returns null for it, and work spawned on it (`this_coro::executor`) is dropped with them. `executor_client::for_current_coroutine()` still takes their worker's io_context.
- **Breaking:** `void wait(const std::set<unsigned>& signals)` → `int wait(std::set<int> signals = {SIGINT, SIGTERM, SIGQUIT})`, which returns the signal received and **no longer stops the workers**: what to do is the application's, as `server.shutdown(grace)` then `workers.stop()`. It stopped them, with their servers and clients, on the first signal. It returns 0 when `stop()` releases it (called from another thread or from one of the workers'), and at once when the workers do not run; with an empty set it waits for `stop()`; several threads may wait at once. While it waits the signals do not take their default action; once it returned they do again. It logs `received signal N` at `info` (it was `received signal N: stopping`). See [Shutdown](README.md#shutdown).
- **Breaking:** `workers::start(n)` returns a `boost::system::error_code` instead of `bool`, **with the meaning inverted** (empty on success): `boost::asio::error::already_started` when they run already (it returned `false`), with no thread added, and `invalid_argument` for 0 threads (it started none and returned `true`). `stop()` returns nothing (it returned `false`, with the same warning, when already stopped). `stop()` may now be called from one of the workers' own threads: that thread ends once its handler returns, and the destructor joins it (and waits for such a `stop()` still joining the other threads).
- **Breaking:** `get_isolated_io_context(name)`, returning an `io_context&`, → `isolated_executor(name)`, returning a `boost::asio::any_io_executor` (`boost::asio::post(executor, ...)`, `co_spawn(executor, ...)`); a null executor when the workers do not run, where it started a thread anyway. Its thread, out of the pool, runs until the workers stop, as before; asking for one while other threads use the workers is no longer a data race.
- `workers::in_worker_thread()` is `const` and answered from a thread-local, without a lock: true on the threads that same `workers` started (of the pool or isolated), false on any other (another `workers`' included) and on its own once stopped. `get_thread_io_context()` takes the caller's io_context from that thread-local, with no mutex per call. `get_next_io_context()`, and `get_thread_io_context()` from a thread that is not one of the workers', throw `std::logic_error` when the workers do not run; they read an empty pool (undefined behaviour).
- The threads of the workers carry their name for the system (`worker thread 1`..., an isolated one its `name`, truncated to 15 characters), as `top -H`, `ps -L` and debuggers show them.
- **Breaking:** `http_frame::kind()` (`http/common/http_frame.hpp`), pure virtual, returns what a frame is on the wire, a `frame_kind`: `head` (`headers`, so `http_request` and `http_response`), `interim` (the `100 Continue`) or `data` (`http_data`). A class derived from `http_frame` must define it. The server asks it instead of casting the frames it writes.
- **Breaking:** `http_stream` owns what happens to the connection once its response is written, its disposition: `disposition()` returns a `detail::after_response` (`keep_alive`, `close` or `take_over`), `must_close(reason)` closes the connection after the response for a `detail::close_reason` (`client_asked`, `http10`, `draining`, `continue_skipped`, `body_unread`, `body_error`, `handler_failed`, `route_timeout`, `framing_by_close`, `aborted`), and `reason()` returns the first reason given. It never goes back to `keep_alive`, and a takeover (`set_takeover()`) stays one. The request only seeds it: the constructor `http_stream(id, bool keep_alive)` is now `http_stream(id, const http_request&)`, or `http_stream(id, detail::close_reason)` for a stream that closes from the start. `keep_alive()` and `set_keep_alive()` are removed, with no alias (see Removed).
- **Breaking:** `response_sink::take_over(response, handler, framing)` takes a `body_framing`: `close` when what the handler writes is the body of the response, ending when the connection closes, so that the sink says so on its head. A sink derived from `response_sink` overrides the new signature.
- The `Connection` header of a response is written by the connection, as it writes the head, from the disposition of its stream: `Close` when the connection closes after the response, whatever the reason, `Keep-Alive` otherwise. A `101 Switching Protocols` keeps its `Connection: Upgrade`, and the `100 Continue` and the body get none. It was copied from the request when the response was built (`send()`, `start_stream()`, the server's own errors...), and set again in a few places that closed the connection later, so a reason to close that came after the response was built and before its head was written was not told: the head said `Keep-Alive` and the connection closed (e.g. a handler failing once its response had started, while the response of a previous pipelined request was still being written). The head now says `Close`. A reason that comes once the head is written still closes the connection after a head that said `Keep-Alive`, as before, since a head written cannot change: a drain beginning while a response is written, a streamed response aborted, or a body left unread by a response sent before the body (a `401` from a middleware) that turns out too large to drop. A `Connection` header the handler sets on its response is still replaced.
- The server no longer changes the request to close its connection: `get_http_request()->keep_alive()` (and `request::keep_alive()`) tells what the client asked, its `Connection` header and HTTP version, also after a body that could not be read, a failed handler, a timeout or a failed upstream body in the reverse proxy, where it returned `false`. Whether the connection closes after the response is the disposition of its stream.
- The responses of an in-memory dispatch no longer carry a `Connection` header (it was `Keep-Alive`, or `Close` for a request that asked for it): there is no connection, and the header is written only as a head goes out on one.
- **Breaking:** a `request` reads its body from a `detail::request_source`, the input twin of `response_sink`, and holds it with its stream, no longer the connection: the constructor `request(std::shared_ptr<server_connection>, std::shared_ptr<http_stream>, std::shared_ptr<http_request>)` is now `request(std::unique_ptr<detail::request_source>, std::shared_ptr<http_stream>, std::shared_ptr<http_request>)`. `request(nullptr, nullptr, http_request)` still builds a request without a connection, which reads no body beyond the read-ahead it is given and has the peer IP set with `set_peer_ip()`, or `""`. A server connection gives its requests a source that sends the `100 Continue` the client waits for at the first read of the body, extends the connection timeout with every byte read and reads nothing once the connection is closing, as the request did; once the connection is gone, a read ends the body (`incomplete`) as before. The request keeps its stream (`get_http_stream()` returns it while the request lives, also once the connection is gone), and the connection lets go of what it kept in the stream for the response once done with it, so a request kept by the handler or the response hook keeps neither the connection nor its socket alive. `request.hpp` no longer includes `server_connection.hpp`.
- **Breaking:** `body_reader::source` returns `awaitable<io_result>` (the error and the bytes read, as `asio::socket::read_some()`) instead of `awaitable<size_t>`, and `body_reader::read_ahead_available()` is now `buffered()`.
- `http_application::dispatch()` serves the body of the request from memory through its source (`detail::memory_source`) instead of storing it as the read-ahead of the request. The handler reads the same bytes, then the end of the body, with the same limits and decoding as on a connection.
- None of the changes to `request` above changes what goes on the wire: the `100 Continue`, the timeouts, the body read, discarded or failed, the closes and the responses are as before, on a connection and in memory.
- **Breaking (B2):** route cancellation is opt-in, through `route::cancel_on()` (see Added). A route timeout still answers `504` (or its status) and lets the handler run to its end, as in 0.8, and the handler now finds `cancelled() == timeout`; on a route declared `cancel_on({cancel_reason::timeout})` it is interrupted instead, its next cancellable await ending with `operation_aborted` (within milliseconds of the `504`). So does a client gone on a route declaring `client_gone`. An interrupted handler is no failure: the exception it ends with is logged at debug level, with no `500` (the timeout answered already, the client is gone, or the connection closes), and a response it had started closes the connection after it. Who notices: a route that opts in, and handlers that want to know why their request is no longer awaited, in `cancelled()`, `client_gone()` or by binding `cancellation_slot()`. Routes that declare nothing behave as in 0.8.1, but for B3–B5.
- **Breaking (B3):** at the drain deadline (`by` of `shutdown(by)`), every handler still running is interrupted (`cancel_reason::shutdown`), whether its route declared `cancel_on()` or not, before its socket closes: its next cancellable await ends with `operation_aborted`. The interruption and the close of its connection run in one call on the connection's thread, so the handler resumes on a closed connection, and nothing it writes then reaches the client. In 0.8 the socket was closed and the handler went on, on its thread, until it ended by itself. `shutdown(by)` still does not wait for the handlers it interrupts, and returns `false` at `by`. Who notices: a handler running at the deadline (a long poll, a call to a slow service), which now stops at its next await; work that must not be interrupted runs outside its cancellation state (see [Cancellation](README.md#cancellation)).
- **Breaking (B4):** the timeout of an in-memory dispatch (`dispatch_options::timeout`) no longer interrupts every handler: `dispatch()` returns `504`, as before, and the scope of the request is cancelled with `cancel_reason::timeout`, which interrupts the handler only if its route declared it (`cancel_on({cancel_reason::timeout})`), as a route timeout does on a connection. In 0.8 its pending awaits were aborted (`operation_aborted`) on any route. A caller cancelling the coroutine awaiting `dispatch()` (a cancellation slot, `||` with a timer) cancels the scope with `cancel_reason::client_gone`, which interrupts only a route declaring it, and the `dispatch()` throws `operation_aborted`. Who notices: a gateway dispatching in memory with a timeout and counting on it to stop the handler (declare `cancel_on({timeout})` on those routes). The comment of `dispatch_options::timeout` says so.
- **Breaking (B5):** a client that closes its sending side after a complete request (a TCP FIN, `shutdown(SHUT_WR)`; over TLS a `close_notify`, or a FIN without one) has not left: its response is written, with `Connection: close`, and the connection closes after it. The server closed the connection as soon as it noticed it, while the handler ran, so the client got no response. A client is gone (`cancel_reason::client_gone`) when it resets the connection, a read or a write on it fails (a reset or a broken pipe as the response is written), or the connection ends in the middle of the request body (its read ends `incomplete`, as before). A client that closes cleanly while its handler runs is noticed later: at the first write of its response (its reset), or at the route timeout. While a handler runs, the connection is the only reader of the socket, once the body was read to its end, and leaves what it reads (a pipelined request, TLS included) for the next request. Who notices: simple HTTP clients (embedded devices, scripts) that shut down their sending side after the request, which now get their response; and tests that ended a client with a FIN to make the server notice it leaving, which now reset the connection.
- **Breaking:** `asio::socket::peer_closed()` returns `awaitable<boost::system::error_code>` instead of `awaitable<bool>`, telling why a readable socket is readable, without consuming anything: no error for data (it stays for the next read), `boost::asio::error::eof` for a FIN (over TLS a `close_notify`, or a FIN without one), the error of the connection otherwise (`connection_reset` for a reset). `true` was any of the last two: `if (co_await s.peer_closed())` keeps its meaning, while `ec == eof` now tells a half-close from a reset. The base class returns `operation_not_supported` (it returned whether nothing was `available()`): a socket defined by an application that can tell overrides it with the new signature, as `tcp_socket`, `unix_socket` and `ssl_socket` do. TCP and Unix sockets now peek one byte (`MSG_PEEK`, never blocking) where they asked for the bytes available.
- **Breaking:** `http_stream` takes the executor of its connection (or of its in-memory dispatch), where its cancellation scope runs: `http_stream(id, request)` → `http_stream(id, request, executor)`, and `http_stream(id, close_reason)` → `http_stream(id, close_reason, executor)`. It is owned by a `std::shared_ptr` (it derives from `std::enable_shared_from_this`).
- The reverse proxy stops the exchange with its target when the scope of the request is cancelled, awaiting `request::client_gone()`, and no longer reads the socket of the client: a client gone stops it as the client leaving (the connection to the target closes, within milliseconds of a reset), and the timeout of the route or the drain deadline stop it as a timeout. A client closing its sending side after its request gets the response of the target, where the exchange stopped (B5).
- **Breaking (B11):** reverse proxy tunnels close after 120 s with nothing forwarded (`proxy_options::tunnel_idle_timeout`, see Added), where they stayed open for ever once both peers went silent or one stopped reading. 120 s sits above nginx's and AWS ALB's 60 s and Cloudflare's 100 s, so a quiet WebSocket is not cut before its keepalive pings, and equals the WebSocket and connection idle timeouts. To keep 0.8's behaviour, set `write_timeout = 0` in the `write_limits` of SSE and WebSocket connections and `tunnel_idle_timeout = 0`. See B11 in [Migrating from 0.8 to 0.9](MIGRATING.md#behaviour-changes-to-check).
- **Breaking:** `sse_connection::handle_write(type, value)` is private. Send each field with its own method: `handle_write("event", x)` → `send_event(x)`, `handle_write("id", x)` → `send_id(x)`, `handle_write("retry", x)` → `send_retry(millis)`, `handle_write("data", x)` → `send_data(x)`, or the whole event with `send(sse_event{...})`. A field of any other type has no counterpart: clients ignore it (WHATWG HTML, Server-sent events); a comment goes with `send_comment()`.
- The queues of `websocket_connection` and `sse_connection` are one internal queue (`detail`), with the same flow control on both: the write limits, the watermarks, `wait_writable()` and the overflow policies behave as before on a WebSocket, the write timeout as B11 below says, and an SSE stream now behaves as a WebSocket does. What an SSE stream counts against `max_messages` and `queued_messages()` is what was sent: each field, as before, and each `sse_event` and each comment, one each, whatever its lines. `drop_oldest` still drops whole events, never the one being written, and never one sent with `send_async()` (or the fields and comments queued before it, which belong to it).
- The SSE keep-alive comment is written once the interval passed since the last write, when nothing is queued nor being written. It was written at the first tick of a timer of that interval with nothing written since the previous tick, so between one and two intervals after the last write.
- `http::write_flow::write_started()` has an overload without an owner, `write_started(on_timeout)`, for a writer that keeps its connection alive until the write finishes. The other is unchanged.
- **Breaking (B11):** `write_limits::write_timeout` is 60 s by default, where it was off, so SSE connections and the WebSocket server connections of `upgrade_websocket()` close a client that stops reading (a WebSocket with `1013`): `on_close()` is called, awaited sends and `wait_writable()` complete with `false`, and the queue is released. 0.8 kept such a client open, its newest events or messages dropped, until it left. Limits given to `set_write_limits()` that do not name `write_timeout` keep the 60 s, nginx's `send_timeout` and `proxy_send_timeout` and the server's `connection_options::write_timeout`. The timeout bounds a stall, a write taking no byte for that long, no longer the whole write of a message: events and messages over 64 KiB are written in 64 KiB slices, each one progress, and the fall of the socket's send backlog counts too, checked once the socket took nothing for the timeout, so only a write that makes no progress for the timeout and a quarter (75 s by default) closes the connection (see Fixed). Changed while a write is stalled, it applies at once, 0 cancelling it. It costs no timer operation per message to a connection whose writes progress. The SSE keep-alive neither moves nor escapes it: it is skipped while a write is pending, and its own write is bounded like any event's.
- **Breaking:** the upgrades of `response` are 8 overloads, one options type and one hand-over type per kind of upgrade (see Added; the old forms are removed, with no wrapper):
  - `upgrade_websocket(handler, const std::set<std::string>& supported_protocols = {})` → `upgrade_websocket(const websocket_accept_options&, handler)`, the options first: `res.upgrade_websocket(h)` → `res.upgrade_websocket({}, h)`, and `res.upgrade_websocket(h, {"chat", "json"})` → `res.upgrade_websocket({.protocols = {"chat", "json"}}, h)`. The subprotocol accepted is the same: the first the client offers that is in the list, `400` for a client offering only others, or any with no protocols, or none with protocols (unless `protocol_required = false`, new). The list is a `std::vector`, no longer a `std::set`.
  - `upgrade_websocket_stream(const websocket_options&, handler)`, and the forms without options, → `upgrade_websocket_stream(const websocket_accept_options&, handler)`, whose handler receives an `upgraded_websocket` instead of the WebSocket and the subprotocol: `[](std::shared_ptr<asio::websocket> ws, std::string protocol)` → `[](http::upgraded_websocket upgraded)`, with `upgraded.stream`, `upgraded.protocol` and `upgraded.scope`; `res.upgrade_websocket_stream(h)` → `res.upgrade_websocket_stream({}, h)`.
  - `http::websocket_options` → `http::websocket_accept_options`, with the same `protocols`, `protocol_required` and `binary`. `ping_interval` and `idle_timeout` are `std::optional`s: setting them (`.ping_interval = std::chrono::seconds(30)`) compiles as before, reading them (`.count()`) does not. Unset, a byte stream still has no keepalive.
  - `take_over(handler)` with a `(std::shared_ptr<asio::socket> socket, std::string buffered)` handler → `take_over(handler)` with an `(http::upgraded_connection conn)` handler: `conn.socket`, `conn.buffered` and `conn.scope`. `takeover_handler` and `takeover_coroutine` are now in `upgrade.hpp`, with that signature, and so is the handler a `response_sink` derived by the application receives in `take_over(response, handler, framing)`.
  - `start_sse(handler)` → `start_sse(handler, const sse_options& options = {})`: calls written as before compile unchanged and behave as before. The handler comes first, unlike the WebSocket upgrades, so that the options can have a default.
- **Breaking:** `http::on_server_shutdown(socket, callback)` → `scope.on_shutdown(callback)`, with the `scope` of the `upgraded_connection` or the `upgraded_websocket`; `set_connection_type(socket, type)` and `wrap_connection(socket, wrapper, type)` → `scope.set_type(type)`. A WebSocket the application builds on the socket of a `take_over()` counts as long as it lives, since it holds the socket: `scope.set_type(connection_type::websocket)` counts it as one. `websocket_connection::on_shutdown()` and `sse_connection::on_shutdown()` are unchanged.
- **Breaking:** `response.hpp` no longer includes `server_connection.hpp`, `http_stream.hpp`, `response_sink.hpp`, `websocket_connection.hpp`, `sse_connection.hpp` nor `<set>`: it declares the types it names, so a file that includes it does not compile the connection internals. `websocket_connection.hpp` and `sse_connection.hpp` include `upgrade.hpp` instead of `connection_tracker.hpp`. A file using those types (calling a `websocket_connection` or an `sse_connection`, `connection_type`, the sink or the stream) includes their headers, or the umbrella `thinger/http_server.hpp`, which still includes them all.
- A connection taken over or upgraded no longer keeps the connection tracker of its server alive: `server_scope` and the tracking hold it weakly, and so does every tracked connection. `tracked_connection::tracker()` (`connection_tracker.hpp`, protected) returns a `std::shared_ptr` by value, null once the tracker is gone.
- What does not change, stated: the message interface of a WebSocket pings after 60 s without receiving anything, closes after 120 s, and takes messages of up to 16 MiB, one byte more closing with 1009, with the default options; a byte stream has no keepalive unless set (`0` is off); the subprotocols negotiated are the same; `stats()` counts the connections taken over, WebSockets, event streams and tunnels as before, until they close; and a takeover while the server already closes its connections closes the connection without calling the handler.
- **Breaking (B6):** a client WebSocket (`client.websocket()`, `async_client` and `executor_client`, synchronous or coroutine) has a keepalive by default, the server's: it pings the peer after 60 s with nothing received, and closes the connection (1001) after 120 s with nothing received. Before, a client never pinged, and its reads and writes waited for ever on a dead peer (lost behind a NAT, a black hole). Change it, or turn it off with `(0, 0)`, with `websocket_client::set_keepalive()` (see Added); the keepalive in force stays on the `asio::websocket` of `release_socket()` (`asio::websocket::set_keepalive()` there). The idle time counts bytes received, so a peer sending a byte within each idle timeout is alive. A connection closed for being idle ends what is pending: `receive()` returns an empty message, `send_text()` and `send_binary()` return `false`, `is_open()` is `false`. Node's `ws` does not ping by default; this library does, as every network wait has a deadline.
- The synchronous calls of `websocket_client` (`send_text()`, `send_binary()`, `receive()`, `close()`) and of `http::client` return once their own operation completes, instead of running the `io_context` until it has no work (which the keepalive never lets happen). With the synchronous API nothing runs between two calls: the keepalive acts at the next one, where bytes that arrived meanwhile count as received, and a check finding the idle timeout passed with no ping sent pings first, closing only if that ping is not answered within the idle timeout minus the ping interval. Both apply to the client role of `asio::websocket` only: a server's keepalive keeps its timing.
- A request costs the server more than in 0.8.1, for what this release does with each one (its cancellation scope, the disposition of its stream, its deadlines): on `benchmark/compare`, the user-space instructions per request are 3 % to 10 % above 0.8.1's (10 % with `Connection: close`), with the same system calls, and the requests per second are 0.91–0.97 of 0.8.1's, depending on the scenario (the medians of 8 rounds, in two runs: `hello` 0.96–0.97, `params` 0.91–0.95, `echo` 0.92–0.97, `close` 0.96). These figures were measured without the connection deadlines (B9), the serving state shared with the connections (B10) and the 421 check, which together add 0.8 % to the user-space instructions of a keep-alive `GET` (about 136 instructions), with the same system calls, and leave the requests per second within the noise of `benchmark/compare` (0.99–1.02 of the build without them, the medians of 16 rounds). This cost is accepted for 0.9.0 at these figures; the remaining reductions are deferred to 0.10. What a request does not use costs it nothing: the signals of a request (the input and cancellation events of its `http_stream`) and those of its connection are created when first needed, and the coroutine that watches the client starts the first time a handler yields with its response unfinished.

- 0.9.0 is not ABI compatible with 0.8 (the changes above, and the layout of several classes): rebuild what links it; the shared library's SONAME is `libthinger_http.so.0.9`. Besides the entries above, the API diff against 0.8.1 (`abidiff` of the shared builds) shows differences that only break the ABI, not the source: the layout of the sockets (the attachment is gone), `http_stream`, `request`, `server_connection`, `websocket_connection`, `sse_connection` and `write_flow`; the virtual functions of the frames (`http_frame::kind()`); `http_stream::set_input_pending(pending)` gains a defaulted `follows`; `async_client::stop()` and `wait()` are no longer virtual, as `worker_client` is gone; the layout of `asio::async_event`, `asio::websocket`, `async_client`, `connection_tracker`, `connection_options`, `route`, `virtual_host` (its settings shared), `http_application` (its serving state shared) and `server_base` (so of `pool_server` and `server`), and of `asio::socket_pipe`, `ssl_socket` (the handshake record) and `proxy_options`; `asio::socket` has two more virtual functions, `send_backlog()` and `misdirected()`, so the virtual tables of every socket (`tcp_socket`, `ssl_socket`, `unix_socket`, `websocket`) change; the body and OpenAPI accessors of `http_application` (`body_decoders()`, `get_body_limits()`, `get_body_settings()`, `get_body_types()`, `get_max_body_size()`, `openapi()`, `set_body_limits()`) and the destructor of `certificate_manager` are no longer inline, with the same signatures; `http_application` has a new protected `connection_handler()`, which gives each connection of the library's servers the shared serving state; and `http_client_base` has one more protected virtual function, `websocket_executor()`, which `async_client` overrides, so the virtual tables of the clients change.

### Fixed

- `socket::connect(host, port, timeout)` of a TCP or TLS socket no longer waits for ever on a peer that accepts the connection and never answers: only the TCP connect was bounded by `timeout`, and the TLS handshake after it, as the name resolution before it, had no deadline, so a peer silent after the accept held the call, and a client calling it directly (an `asio::websocket` over an `ssl_socket` included) hung for weeks. The call now takes one absolute deadline when it starts, and the resolution, the connect and the client handshake each run with the time left: on expiry, in any phase, the socket is closed and `timed_out` returned (`operation_aborted` when the caller cancelled it); other errors are returned as before. The bound of the resolution is best-effort, as asio cannot interrupt `getaddrinfo` (a numeric host with a numeric port is not resolved). The TLS handshake of a server (listener) is unchanged. See the contract of `connect()` in `socket.hpp`. The HTTP clients were bounded already by their request timeout.
- A handler that moved to another executor (`co_await boost::asio::post(other)`, or offloading) and then read its request body sent the `100 Continue`, read the socket and moved the connection's idle deadline from that thread, racing the connection's own thread (ThreadSanitizer reported it); the end of the body was marked from there too. The read now runs on the thread of the connection, and the handler resumes on its own executor; a body still arriving within the idle timeout keeps the connection open, as on the connection's thread. A handler reading on the connection's thread, the common case, pays nothing more.
- The sockets a listener accepts are close-on-exec, on both accept paths (on its acceptor thread, `accept4()` with `SOCK_CLOEXEC` on Linux and `fcntl(FD_CLOEXEC)` elsewhere; with executor providers, `fcntl(FD_CLOEXEC)` once accepted), before they reach the handler: a process a handler forks and executes no longer inherits the connections. The listening socket itself is not close-on-exec yet.
- A client request cancelled between two of its operations (its coroutine cancelled, e.g. by a cancellation slot or `||` with a timer, when one operation had completed and the next had not started) failed with `invalid_argument`, or a streamed one with the message of an empty error code ("Success"), instead of `operation_aborted`: asio ends such a cancellation with an exception at the next `co_await`, which the request's race against its timeout discarded. The request now ends with `operation_aborted`, whichever its phase.
- `async_client::run()`: a coroutine ended by an exception stayed counted as pending, so `wait()` waited for it forever (and `wait_for()` until its timeout). It is now counted as ended.
- An exception thrown inside a synchronous call of `http::client` (`get()`, `post()`, `send()`...) or `websocket_client` (`send_text()`, `send_binary()`, `receive()`, `close()`) is rethrown to the caller. It was lost: the client returned an empty response, and the WebSocket client waited forever.
- A request made with `request(url)` (the `request_builder`) on a client set to a Unix socket with `unix_socket(path)` ignored it, streamed or not, and connected over TCP to the host of the URL; only the requests of `get()`, `post()` and the other shortcuts, and of `create_request()`, reached the socket. The client's socket now applies to every request that does not name its own (`request_builder::unix_socket()`).
- `websocket()` on a client set to a Unix socket (or given a request naming one) ignored it and connected over TCP to the host of the URL. The WebSocket now opens over the socket, as the other requests do.
- A connection taken over that asks to be told of a shutdown once the drain started is told: its callback is posted once to the io_context of the socket. It was never called, since the drain had already passed it by: e.g. a `websocket_connection` from a coroutine `upgrade_websocket()` handler still running when the drain started (it starts once the handler completes) was not closed with 1001, and stayed open until the deadline of the shutdown. A callback set while the handler of the takeover runs is still called when the handler returns, as before.
- A WebSocket message of the message interface within the limit (16 MiB by default), sent in several frames, one of which ended less than 1 KiB under the limit, was closed with 1011 (Internal Error): the next read asked the buffer for 1 KiB past the limit, which it refused with an exception. The reads now stop at the limit, so such a message is delivered, and one going past the limit closes with 1009 (Message Too Big), as a single frame larger than the limit does.
- A `pool_server` stopped or destroyed while its workers ran left its connections open on them, each with a handler holding a raw pointer to the server: the next request of a keep-alive connection, a handler still running (after a shutdown whose deadline expired too), or the coroutine of a route with a timeout used the freed server (heap-use-after-free under ASan). 0.8.1 had it too, and following the README, which tells applications to stop or destroy their servers before the workers, reached it. The connections now share the server's serving state instead, and `stop()` closes them (B10 in Changed).
- A client trickling a request head or body, or not reading its response, held a server connection for days or for ever, as only the idle timeout bounded it and every byte moved it; the header, request and write deadlines of `connection_options` now bound it (B9 in Changed).
- The certificate of an exact host name was matched as a regex: `api.example.com` was also served for `apiXexample.com`. Exact names now match only themselves (see Changed); the client certificate modes of `set_client_verify()` match the same way.
- Certificates were looked up case-sensitively, though the README said otherwise: a handshake for `Api.Example.com` got the default certificate instead of the one of `api.example.com`. Lookups (`get_certificate()`, `has_certificate()`, `remove_certificate()`, the SNI selection) and the default host comparison of `set_certificate()` are case-insensitive.
- A handshake that matched no exact name tried every registered name as a regex, so its cost grew with the names; a lookup now probes one exact name and one wildcard, without a regex.
- A certificate name that did not compile as a regex was dropped silently, after `set_certificate()` had logged it as set and returned success; it is now refused with `invalid_argument`.
- An SSE client that stopped reading looked alive for ever: its write blocked, new events were dropped, and the keep-alive comment waited behind the stalled write. The write timeout now closes it (B11 in Changed).
- A write timeout set on an SSE or WebSocket connection cut a slow client that kept reading a large event or message, as it bounded the whole write of each one. It now bounds a stall, so a client that keeps reading is never cut (B11 in Changed).

### Security

- The client certificate mode of a host name (`certificate_manager::set_client_verify()`, since 0.8.0) did not protect its virtual host on a TLS listener shared with other hosts: the mode was chosen by the SNI name of the handshake, the virtual host by the `Host` of each request, and the two were not compared, so the per-host client certificate requirement could be bypassed when SNI and `Host` differ. An HTTPS request whose `Host` gets another client certificate mode (either way) or, with SNI, another certificate entry than its SNI name is now answered `421 Misdirected Request` before any middleware, route, upgrade or handler runs, without reading its body; it is logged at debug level. The same name, names sharing one configuration, and clients without SNI on the listener's mode are served as before; plain connections and in-memory dispatch are not checked. A connection whose manager is gone since its handshake serves only the requests for its SNI name. See [The certificate manager](MIGRATING.md#the-certificate-manager).

## [0.8.1] - 2026-10-23

### Added

- `sse_connection::set_keepalive(interval)`: a comment (`: keep-alive`) sent every `interval` the stream was quiet, 15 s by default (`DEFAULT_KEEPALIVE_INTERVAL`), 0 to disable; `send_id()`. See [SSE Server](README.md#sse-server).
- `asio::websocket::write_message()`: one message, as `write()`, an empty one included.

### Fixed

- SSE fields were written unchanged, so a value with a line break (pretty-printed JSON, user text, a device payload) broke the framing: the client took each following line as a field, and `"x\nevent: admin\ndata: ..."` injected an event. `send_data()` now sends each line of its value (split on CRLF, CR or LF) as a `data:` field of its own, as the WHATWG specification requires, so the client gets the value as sent (line breaks as LF). `send_event()`, `send_id()` and `handle_write()` refuse a value with CR or LF (and an ID with NUL), logging an error and returning `false`, instead of sending it.
- An SSE stream was closed after 60 s without sending anything, so a quiet stream (e.g. an IoT dashboard waiting for changes) died every minute. It now sends a keep-alive comment instead (see Added); a client gone is still noticed by reading the connection.
- The connect timeout of `tcp_socket` and `unix_socket` was a coroutine detached from `connect()` holding references to its frame: when the timer completed along with the connection, it could run after `connect()` returned, writing to the freed frame and cancelling the next operation on the socket (the TLS handshake of an `ssl_socket`). The connect and its timer now race with `||`, both ended before `connect()` returns, in one helper (`asio::with_timeout()`); a connect timed out closes the socket.
- An empty WebSocket message (a frame without payload, valid per RFC 6455) could not be sent: `websocket_connection::send_text("")` and `send_binary("")`, and the client's `send_text("")` and `send_binary()` of nothing, sent nothing. They now send it.
- The WebSocket client took an empty message from the server as the end of the stream: `run()` stopped reading and called `on_close()` while the connection was open. It now delivers it to `on_message()`, and ends when reading fails (the connection closed or lost).
- `asio::websocket::cancel()` could leave the pending read waiting forever. When the socket read under it had completed already, its handler not run yet (e.g. with a ping from the peer), the socket had nothing left to cancel, and the websocket handled the control frame and read the socket again: a `read_some()` cancelled while the peer kept pinging never returned, and a `websocket_connection` released with `release_socket()` could go on reading the socket handed to its new owner. The read now ends with `operation_aborted` before it reads the socket again (or returns the data it received meanwhile). It made the test of client WebSockets on strands of a multi-threaded `io_context` hang now and then, in 0.8.0 as in 0.8.1.

## [0.8.0] - 2026-10-22

### Added

- Client certificates on TLS servers (mutual TLS): `tcp_socket_server::enable_ssl(bool, asio::client_verify_options)`, with the mode (`asio::client_verify`: `none`, `optional`, `required`), the trusted CAs (PEM; none for deferred validation: the handshake accepts any well-formed chain once the client proves it holds the key of its certificate, and the application validates the chain), `max_depth` (4) and `max_cert_list` (16 KiB, the memory a client may use before it is authenticated). With trusted CAs a certificate presented that does not validate fails the handshake, also in `optional` mode. It returns `false` if the trusted CAs cannot be read, and the server then serves no connection. The mode is set on each connection, never on the context listened with, which other listeners may share. See [Client Certificates](README.md#client-certificates).
- `certificate_manager::set_client_verify(hostname, mode)`, `remove_client_verify()` and `get_client_verify()`: a mode of its own for a host name (SNI), exact or `*.domain` as the certificates, case-insensitive, applied in the SNI callback; other hosts keep the mode of their listener. A session resumed without a certificate on a host that requires one fails the handshake.
- `asio::tls_session` and the virtual `socket::tls()`: the version, cipher, server name (SNI), whether the session was resumed, the certificates of the peer (DER, its leaf first) and the result of their validation, once the handshake is done; `std::nullopt` for a plain socket. A WebSocket answers for the socket it runs on. `ssl_socket::peer_certificate()` and `peer_chain()`: the certificate and chain of the peer, without copies.
- `tcp_socket_server::set_handshake_timeout()` and `get_handshake_timeout()`: how long a TLS client has to complete its handshake (see Changed).
- `on_close()` on the WebSocket used as a socket (`asio::websocket`, `upgrade_websocket_stream()`), with an `asio::websocket_close` (`http::websocket_close` is now an alias of it): called once, whatever closed it (its close frame, `close()`, the keepalive, a protocol error, a lost connection, the socket closed by a server shutting down), with the guarantees of `websocket_connection::on_close()`. See [WebSocket Close](README.md#websocket-close).
- Client certificates on the HTTP and WebSocket clients: `client_certificate(certificate, key, chain)`, `client_certificate_file(...)`, `clear_client_certificate()` and `has_client_certificate()`, presented on every TLS connection of the client (requests, WebSockets, proxy tunnels). Checked when set: `client_error::invalid_client_certificate`, `invalid_client_key` (an encrypted key included) or `client_key_mismatch`, and the current one is kept. See [Client Certificates](README.md#client-certificates-1).
- `asio::use_certificate(context, chain, key)`: the loader of a certificate and its key the server and the client share, which checks that the key is the certificate's.

### Changed

- A TLS client has 60 seconds (nginx's `ssl_handshake_timeout`) to complete its handshake once accepted by a `tcp_socket_server`, the HTTPS servers included: the connection is closed otherwise, without reaching the handler. There was no limit, so a client that sent nothing held its connection until it left. `stop()` also closes the connections whose handshake is pending, which no longer reach the handler once it returns.
- Handshakes that fail are logged as warnings (they were errors), and those that time out at debug level: any client causes them.
- Every context of `certificate_manager` (created, or given with `set_certificate()` and `set_default_certificate()`) gets the session id context `thinger-http`, so sessions with client certificates can be resumed; a listener asking for certificates sets one of its own on each connection.
- Private keys are read without a password callback: an encrypted key fails with an error instead of asking for its password on the terminal (OpenSSL's default), in `certificate_manager` too.
- `close_notifier` moved to `thinger/util/close_notifier.hpp` (`thinger::util`); the old header still includes it, as an alias.

### Deprecated

- `tcp_socket_server::enable_ssl(bool, bool client_certificate)`: use `enable_ssl(bool, client_verify_options)`. `true` asks for an optional certificate with deferred validation (it did nothing before); `enable_ssl()` and `enable_ssl(true)` take the new overload.

## [0.7.1] - 2026-10-19

### Added

- `http::server::set_lingering_close(max_bytes, timeout)` (static, for every server of the process, so that the classes keep the layout of 0.7.0 and its ABI): how long a connection closing with its request still arriving reads and drops it (see Fixed). 8 MiB and 5 s by default; 0 for either closes at once, as before.

### Fixed

- A connection closed after a response while the client was still sending its request (a body over the limit answered `413` before it was read, `417`, a `401` from a middleware before a body too large to discard, a request timeout, a chunked body going past the limit, a header section too large) was closed with the body unread: the system answered the data still arriving with a reset, so a client still sending got `EPIPE` or a connection reset, and never read the response (e.g. 4 MiB sent to a route limited to 64 KiB). The server now closes such a connection gracefully (RFC 9112 section 9.6): once the response is written it stops sending, reads and drops what keeps arriving until the client closes, up to 8 MiB or for 5 s at most, and then closes. Its memory does not grow meanwhile, and a graceful shutdown does not wait for it. A body within the limit left unread is still dropped to keep the connection alive, as before. See [Limits and Timeouts per Route](README.md#limits-and-timeouts-per-route).
- The client reads the response a server sent before the request was written whole, when writing the rest fails because the server closed the connection (`EPIPE` or a reset), as curl does: it returned the write error. A `408` read that way on a reused connection is taken as the server closing it while idle, and the request is sent once more on a new one, whatever its method, as it was not processed.

## [0.7.0] - 2026-10-19

### Added

- `on_close()` on the server WebSocket (`websocket_connection`) and SSE (`sse_connection`) connections: called once the connection closed, whatever closed it (the peer, a lost connection, `stop()`, the server shutdown, the overflow policy, a write timeout...), once, posted to the thread of the connection (never from within the call closing it), what it throws logged; set once the connection closed, it is posted at once. The WebSocket one receives a `http::websocket_close`: the status code of the peer's close frame and its reason, or the code the server closed with, or 1006 if no close frame was exchanged, and whether the peer closed first. An `sse_connection` reads its client, only to notice when it leaves, so the producer learns it at once, not at its next event: a client half-closing the connection (EOF) has left too. See [WebSocket Close](README.md#websocket-close).
- `asio::websocket::get_close_code()`, `get_close_reason()` and `closed_by_peer()`: the closing handshake, once closed; `CLOSE_NO_STATUS` (1005), `CLOSE_ABNORMAL` (1006) and `CLOSE_INTERNAL_ERROR` (1011).
- `request::get_request_scheme()`: `"http"` or `"https"`, the scheme of the connection, or, when the peer is a trusted proxy, the one it forwarded for the client of `get_request_ip()`, in the same walk: the `X-Forwarded-Proto` value aligned with the `X-Forwarded-For` entry of the client (or its last value when they have not as many), or the `proto` of the `Forwarded` element of the client (RFC 7239). `trusted_proxies::resolve()` (address and scheme at once) and `parse_scheme()`. See [Client IP Behind Proxies](README.md#client-ip-behind-proxies).
- `http_application::on_response(hook)`: called once per request with its response (`http::response_info`: status, bytes written, duration, and whether it completed, handed the connection over or was aborted, and was streamed), whoever answered it, the server's own errors included, once the response ended and the application is done with the request. It costs nothing without a hook. See [Response Hook](README.md#response-hook).
- `request::get_http_request() const`, returning a `std::shared_ptr<const http_request>`.
- TLS options of the server contexts: `asio::tls_options` (minimum and maximum versions, TLS 1.2 ciphers, TLS 1.3 cipher suites, server cipher preference, groups and OpenSSL security level), `certificate_manager::set_tls_options()` and `get_tls_options()`, and `asio::apply_tls_options(context, options)` for contexts made elsewhere. They apply to every context the manager creates, the certificates selected by SNI included. See [TLS Settings](README.md#tls-settings).

### Changed

- TLS defaults: the contexts `certificate_manager` creates follow Mozilla's "intermediate" configuration, as Node and nginx: TLS 1.2 and 1.3 only, ECDHE with AES-GCM or ChaCha20-Poly1305 for TLS 1.2, and the client's cipher preference. They allowed from TLS 1.0 (refused by the default security level of OpenSSL 3, not by the server) and OpenSSL's default ciphers, CBC and those without forward secrecy included. Clients without TLS 1.2 (Android before 4.4.2, Java 7, Internet Explorer 10 and older) are refused; `enable_legacy_protocols(true)` still allows TLS 1.0 and 1.1 (with OpenSSL's default ciphers unless others are set). `set_server_ciphers()` and `enable_legacy_protocols()` are deprecated: they change the TLS options, validated (`set_server_ciphers()` returns `bool`), in any order; `enable_legacy_protocols(false)` undoes only what `true` did, and the server cipher preference no longer requires a cipher list.
- A server WebSocket whose `on_message()` throws is closed with 1011 (Internal Error), the exception logged: it stopped reading, and was left open.
- A server WebSocket whose read fails (the connection reset, or ended without a close frame) is closed, instead of being left open, unread, until released.
- `websocket_connection::release_socket()` called from `on_message()` stops reading the socket at once: the WebSocket read the next message from the socket released.
- An in-memory dispatch that times out completes the response with the 504 it returns, so a late answer is dropped; a response that completes in the meantime is returned instead of the 504.
- Fewer allocations answering: `response::header(key, value)` takes its key and value by value, moved into the response (callers do not change; pass an rvalue to save the copy), and the answer sent moves the status and headers set before answering into its message instead of copying them. A header set before answering costs one allocation for a long value passed as an lvalue, and none when moved in, instead of five: a response with a 36-character `X-Request-Id` took 8 allocations (3 without it), and now takes 4, or 3 with the value moved in. Each answer claims the response before building its message, so `json()`, `encode()` and `send_file()` encode or read the body first (an error answered instead still has the headers set). `http_frame`, `headers` and `http_response` are movable: moving one copied it.

- 0.7.0 is not ABI compatible with 0.6.0 (the signature of `response::header()`, the virtual functions of `response_sink`, the layout of several classes): rebuild what links it. The shared library's SONAME carries the minor version while on 0.x (`libthinger_http.so.0.7`), so the next ones do not load in its place. The overload `request::get_http_request() const` makes `&request::get_http_request` ambiguous: cast it to the one wanted.

## [0.5.0] - 2026-10-17

### Added

- `executor_client`: an HTTP client running on an io_context the caller already runs, usually the one of the calling coroutine (`executor_client::for_current_coroutine()`), with no threads of its own and no idle timers. Its requests run on the caller's thread and are cancelled with the coroutine awaiting them; it keeps no idle connection by default and closes its connections when destroyed. For occasional calls from server coroutines; a pooled client (`async_client`) suits many calls to the same host. See [Executor Client](README.md#executor-client-executor_client).
- `asio::io_context_of(executor)` (`<thinger/asio/io_context_of.hpp>`): the io_context of an io_context executor or of a strand of one, null for other executors.

### Changed

- Quieter startup and shutdown logs. At `info`, a server logs where it listens (`listening on http://0.0.0.0:8080`, `https://...` or `unix:/path`, with the port bound), when a graceful shutdown starts (`shutting down the server on http://0.0.0.0:8080: 2 connections open, grace period of 30000 ms`) and when it stopped (`server on http://0.0.0.0:8080 stopped`, also after `stop()` without a shutdown), one line each, as Node and Go servers do; the workers log the signal received and what it does in one line (`received signal 15: stopping gracefully, within 30000 ms (a second signal stops at once)`). The rest moved to `debug`: a line per connection accepted (`received connection from: ip: ...`, `received connection on Unix socket: ...`), a line per worker thread stopped, worker clients registered and unregistered, the steps of the workers starting and stopping, acceptors starting and stopping, and the socket servers' own `TCP server is now listening` (`Unix socket server ...`, `Standalone server ...`), which said `TCP` for TLS too. Warnings and errors did not change. See [What a Server Logs When It Starts and Stops](README.md#what-a-server-logs-when-it-starts-and-stops).

### Fixed

- The connect timeout of the TCP and Unix sockets runs on the executor of the coroutine connecting, as the connect does. It ran on the io_context of the socket: from a strand of an io_context run by several threads, it could cancel the socket on one thread while the connect used it on another.
- The library builds on macOS with Apple clang (libc++) and OpenSSL 3.6: the self-signed certificate wrote into the subject name OpenSSL now returns as const, and the key of the client's TLS contexts printed a file time count that is a 128-bit integer with libc++.

## [0.4.0] - 2026-10-16

### Added

- Flow control for the server WebSocket (`websocket_connection`) and SSE (`sse_connection`) connections, for streams between a fast and a slow end. See [WebSocket Flow Control](README.md#websocket-flow-control).
  - `send_text_async()` and `send_binary_async()`: awaitable sends that complete once the message is written to the socket (never dropped).
  - `set_write_limits()` with a `http::write_limits`: limits of the queue in messages and in bytes, high and low watermarks (`on_high_watermark()`, `on_low_watermark()`, told asynchronously, and `wait_writable()`), the overflow policy of the messages sent without waiting: `drop_newest` (the default, as before), `drop_oldest`, or `close` (WebSocket `1013 Try Again Later`), and an optional `write_timeout` closing a client that stops reading. `queued_bytes()` and `queued_messages()` (atomic, readable from any thread) tell what is not written yet; `queue_full()` tells whether the next message overflows. SSE drops whole events.
  - `pause_reading()` and `resume_reading()`: a WebSocket stops reading its socket, so TCP backpressure reaches the client, and goes on in order. The keepalive is suspended while paused.
- `log_bodies(enabled, max_length)` on the server (`http_server_base`) and the client (`http_client_base`): an opt-in for debugging that logs the header values and the start of the bodies of the requests and responses, up to `max_length` bytes (1024 by default), with control characters escaped. See [What the Message Logs Show](README.md#what-the-message-logs-show).
- `logging::should_log(level)` and `LOG_INFO_ENABLED()`, `LOG_DEBUG_ENABLED()`, `LOG_TRACE_ENABLED()`, to skip building a costly log message.
- `asio::websocket::close(code)` is public, with `CLOSE_TRY_AGAIN_LATER` (1013), `CLOSE_INVALID_PAYLOAD` (1007) and `CLOSE_MESSAGE_TOO_BIG` (1009); codes that may not be sent (1005, 1006, 1015...) are sent as 1000. `get_ping_interval()`/`get_idle_timeout()` tell the keepalive settings.
- Benchmarks `benchmark_ws_echo` (echo throughput) and `benchmark_ws_slow_reader` (memory with a slow reader, by producer mode).

### Changed

- `asio::websocket::set_keepalive()` counts the idle time from the call.
- Received close codes 1012 to 1014 (IANA registry) are valid, as in Node ws and Go: they were answered as a protocol error (1002).
- A server WebSocket whose write fails is closed, and the messages queued are discarded, instead of being kept until the connection was released.
- A server WebSocket receiving invalid UTF-8 text closes with `1007`, and one receiving a message larger than its buffer with `1009`, instead of only stopping to read.
- `http_frame::log(scope, level)` is `log(scope, options)`, with a `http::body_logging` (the level was not used). A frame without a log of its own, as the body chunks of a streamed response, logs nothing: it logged a warning for every chunk.

### Removed

- `websocket_connection::congested_connection()`: use `queue_full()`.

### Security

- The HTTP logs no longer show bodies, header values or WebSocket messages, which may hold credentials. The client and the server logged the bodies at `trace` level, and the header values at `debug` level, Authorization and Cookie included; the server WebSocket logged every message received (hex encoded) at `debug` level. They now log the request line or the status, the header names and the body size; bodies and header values only with `log_bodies()`, and the values of `Authorization`, `Proxy-Authorization`, `Cookie` and `Set-Cookie` never. Nothing is formatted unless its level is logged.
- The logged request lines and URLs redact the values of query parameters that carry credentials (`access_token`, `authorization`, `token`, `api_key`, `apikey`, `key`, `password`, `client_secret`) and the password of the user info: `GET /data?authorization=[redacted]&count=10`. `http::util::url::loggable_uri()` does it.

## [0.3.0] - 2026-10-14

### Added

- Request context: typed values a middleware stores in the request for the route handler, such as the authenticated principal (`req.context().set(key, value)`, `req.context().get(key)`), as Express `res.locals`, Go `context.WithValue` or Rust `http::Extensions`. Values live under `http::context_key<T>` keys, told apart by their address, so two values of the same type do not collide; move-only values are supported, and they are destroyed with the request. Every kind of middleware and route callback sees them, and in-memory dispatch too, which seeds them with `dispatch_options::context`. A request storing nothing allocates nothing for it. See [Request Context](README.md#request-context).

### Changed

- `certificate_manager::set_default_certificate(certificate, key)` returns `bool`, and keeps the current default certificate when they are not valid, instead of removing it.
- `certificate_manager::get_default_host()` returns a copy (`std::string`), as the reference returned could change while it was read.
- The manager installs its SNI callback on the contexts it creates, and on those given to `set_default_certificate()` and `set_certificate()`, when they are created or set. The servers no longer install it as they start listening (`tcp_socket_server::set_sni_callback()` is still there for other contexts).
- A TLS handshake with a host name (SNI) without a certificate of its own logs at debug level, instead of a warning per handshake.

### Fixed

- TLS: replacing the default certificate (`certificate_manager::set_default_certificate()`) while a server listens applies to the next handshakes without SNI or with a host name without a certificate, as Node's `setSecureContext()` and Go's `GetCertificate` do. They got the default certificate of when the server started listening until a restart (e.g. after an ACME renewal). Connections keep the certificate they took.
- `certificate_manager`: certificates created while the cipher list or the legacy protocols were being changed read those settings without the lock.
- TLS: a server starting to listen wrote the SNI callback into the default context, shared with the servers already handshaking on it (a data race).

## [0.2.0] - 2026-10-14

### Added

- Precompressed static files: `serve_static()` sends a file as its `<file>.br` or `<file>.gz` sibling to the clients accepting `br` or `gzip` (by `q` value, `br` first at equal quality), if the sibling is a regular file not older than the file, with `Content-Encoding`, the `Content-Type` of the file, `Vary: Accept-Encoding` and an `ETag` of its own (`W/"...-br"`); conditional requests, `HEAD` and byte ranges apply to it. On by default (`static_options::precompressed`).
- Lists of content codings (`Content-Encoding: deflate, gzip`) are decoded in reverse order, by the client and by the server, up to five of them; a list with a coding that is not supported is kept as it is (`util::decode_content`).
- `deflate` bodies without the zlib header (raw deflate) are decoded, as curl and browsers do.
- `parse_accept_encoding()`: the quality `Accept-Encoding` gives gzip, deflate, br and identity.
- `Expect: 100-continue` (RFC 9110 section 10.1.1): the server sends `100 Continue` when the body is first read, by the server or by the handler, in order with the pipelined responses, so curl uploads no longer wait a second for it. A request answered without reading its body gets no `100 Continue`, and its connection is closed after the response, as Go and Node do. The reverse proxy sends it once it starts streaming the body to the target.
- `417 Expectation Failed` (`http_response::status::expectation_failed`) for any expectation other than `100-continue`, as Node and Go answer. `http_request::get_expectation()` tells the expectation of a received request.
- multipart/form-data bodies (file uploads), parsed as they arrive without holding the body in memory: `req.read_multipart()` gives the fields and writes the files to temporary files, deleted with the form unless moved (`move_to()`) or kept (`release()`); `http::multipart_reader` streams the parts and their content, like Go's `multipart.Reader`; `http::multipart_parser` is the incremental parser under both. Limits on parts, files, header sections, filename, field and file sizes (`413`), strict RFC 7578 / RFC 2046 syntax (`400`), `filename*`, and safe filenames against path traversal. See [File Uploads](README.md#file-uploads-multipartform-data).
- `multipart` body decoder, for routes that `accepts({"multipart"})`: the same object as a urlencoded form, files as objects with their content.
- Fuzz target `fuzz_multipart`, with its seed corpus.

### Changed

- gzip bodies are decoded whole: every member of concatenated gzip data, instead of the first one only, with the size limit on all of them. Bytes after the last member (other than zero padding), and after the end of a deflate stream, now fail to decode (`client_error::bad_content_encoding`, or `400` for request bodies) instead of being ignored.
- `util::gzip::decompress()` and `util::deflate::decompress()` take a `std::string_view`.
- Client: the synchronous `client` also closes its expired idle connections as a request ends, not only as the next one starts, so they no longer wait for the next call after a long request, nor take the room of other connections in the pool. Between calls they still stay open until the next call (as in curl and urllib3): `clear_connections()` closes them.
- A request with `Expect: 100-continue` answered without reading its body (e.g. `401` from a middleware) closes the connection after the response (`Connection: close`), instead of discarding the body, which the client may never send. A request with another expectation is answered `417` before the middlewares and the handler run. `Expect` in HTTP/1.0 requests is ignored, as before.
- The built-in body decoders include `multipart`: a route taking the body decoded that accepts `multipart/form-data` (by that media type) decodes it now, where it answered `415` for lack of a decoder. Routes that do not list it are not affected; `body_decoders().remove("multipart")` restores the previous behavior.
- Internal reorganization of the server responses, without behavior changes: the reverse proxy is split by concern (`reverse_proxy/`), file responses and static files move to `file_server/`, and response compression to `response_compression.hpp`, which now declares `parse_accept_encoding()` and `negotiate_content_coding()` (`body_decoders.hpp` still includes it).

### Fixed

- `Content-Encoding` names are case-insensitive and `x-gzip` is gzip when decoding responses (client) and request bodies (server), as RFC 9110 says; only `gzip` and `deflate` in lowercase were decoded.
- Client: multipart forms percent-encode `"`, CR and LF in field names and filenames, as browsers and curl do. Before, a filename with a quote or a line break could end the `Content-Disposition` parameter or header and inject others.

### Removed

- `thinger/util/gzip.hpp`, a legacy header (the global `Gzip` class, on CryptoPP and Boost.Iostreams) that nothing used and did not compile on its own. Compression is in `thinger/util/compression.hpp` (`util::gzip`, `util::deflate`).

## [0.1.0] - 2026-10-14

First tagged release. Until now the library was used from `main`.

### Server

- HTTP/1.1 server on Boost.Asio coroutines, served on a pool of worker threads or standalone, over TCP, TLS (with per-domain certificates through SNI) and Unix sockets.
- Routing on a tree of path segments: path parameters with constraints, query parameters, route groups, and documentation fields and free metadata per route.
- Synchronous and coroutine handlers. Handlers can take the JSON body already parsed and validated against a JSON Schema.
- Request bodies decoded by `Content-Type` (JSON, msgpack, CBOR, UBJSON, forms), with limits on size, nesting and values. Bodies can be read whole, deferred or streamed.
- Middlewares, synchronous or coroutines, Express style.
- Body size, decoding limits and timeout per route, group and virtual host.
- OpenAPI 3.1 documents generated from the routes.
- In-memory request dispatch, without a socket, with a timeout that cancels the handler.
- Virtual hosts, a configurable error format, and the client IP behind trusted proxies.
- Static files with `ETag`, `Last-Modified`, `304 Not Modified`, byte ranges (`206`, `416`), `Cache-Control` and an SPA fallback.
- `HEAD` answered by the `GET` routes, without a body. `405 Method Not Allowed` with `Allow`.
- Response compression (gzip, deflate) negotiated as RFC 9110 says (q-values, `identity`, `*`), with `Vary: Accept-Encoding`, as Express's `compression` does.
- Streaming responses with flow control, chunked responses, Server-Sent Events, WebSocket, and taking a connection over (also per stream).
- WebSocket as a byte stream socket, for tunnels and other protocols over it.
- Reverse proxy to HTTP, HTTPS and Unix socket targets, streaming bodies both ways and tunneling WebSockets.
- Graceful shutdown: stop accepting, drain the requests in progress within a grace period and notify WebSocket and SSE connections. `workers::wait_graceful()` does it on `SIGINT`/`SIGTERM`, and stops at once on a second signal.
- Connection statistics by kind (HTTP, WebSocket, SSE, tunnels, taken over).

### Client

- Synchronous `client` and `async_client` (callbacks or coroutines), with a fluent request builder, redirects, streaming and file downloads, Unix sockets and WebSocket.
- Keep-alive connection pool: idle connections reused per origin, bounded per host and in total, closed after an idle timeout (shortened to the server's `Keep-Alive: timeout`), checked before reuse, and requests retried once on a new connection when that is safe (as Go does).
- HTTP proxies: absolute-form for `http://`, `CONNECT` tunnels for `https://`, `ws://` and `wss://`, Basic proxy authentication, and the `http_proxy`, `https_proxy`, `all_proxy` and `no_proxy` variables (uppercase too, except `HTTP_PROXY`, never read, as curl does, against httpoxy).
- Additional trusted CAs (files or PEM), with or without the system ones.
- Responses parsed as strictly as requests, with an error code for each way a response can be wrong (`client_error`).
- gzip and deflate bodies decoded within the maximum content size (no decompression bombs); a body that cannot be decoded fails with `bad_content_encoding`.
- `TCP_NODELAY` on client connections.

### Robustness

- Strict request parsing and framing (RFC 9112): `Content-Length` and `Transfer-Encoding` rules, no obsolete line folding, ASCII request targets, bounded header sections and bodies.
- Fuzzing with libFuzzer of the request and response parsers, the chunked decoder, the body decoders, URL decoding and gzip/deflate decoding, and differential fuzzing against llhttp and Boost.Beast.
- Test suite run in CI in Release and with AddressSanitizer, UndefinedBehaviorSanitizer and ThreadSanitizer, plus CodeQL and coverage.

### Changed (for users tracking `main` before 0.1.0)

These changes of the last weeks can be noticed by code written against an earlier `main`:

- A coroutine lambda passed to a callback that is only called, never awaited (`sync_callback`, e.g. `on_message`, `on_shutdown`, error formatters, hooks), no longer compiles. Before, it compiled and never ran. `use()`, `take_over()`, `upgrade_websocket()`, `start_sse()` and the client callbacks now run coroutines.
- A route with `.schema()` validates the body whatever the handler signature (400 when invalid, 415 when its type cannot be decoded). Before, a handler taking `(request&, response&)` skipped the validation.
- Responses sent whole always carry the `Content-Length` of their content and never `Transfer-Encoding`. 1xx and 204 have no body nor `Content-Length`, and 304 has no body.
- Responses of `take_over()` that are not framed, and event streams, say `Connection: close`.
- `Vary: Accept-Encoding` is added to compressible responses even when they are not compressed. `Accept-Encoding: gzip;q=0` is honoured, and `Cache-Control: no-transform` disables compression.
- The reverse proxy answers 504 instead of 400 when its timeout ends while it streams the request body.
- Client: `auto_decompress(false)` keeps bodies as received; before, a compressed body was decoded anyway. A body that cannot be decoded fails with `client_error::bad_content_encoding` instead of being returned undecoded.
- Client: streamed requests (`send_streaming()`, `download()`) ask for `Accept-Encoding: identity` and are never decoded. `stream_result::headers` is filled (names in lowercase).
- Client: connections are kept alive between requests (see the README to tune or disable the pool).
- The unused `request_handler` interface was removed.
